# Agent Note: Replay-verified checkpoint freshness for the context graph

Status: proposed

English | [中文](2026-09-05-context-graph-replay-verification.zh.md)

## Problem

`@deepseek-ai/dsh-context-graph`'s freshness classification (`fresh`/`aging`/`stale` in `src/graph.ts`) is purely age-based: a node younger than half its configured lifetime is `fresh` regardless of whether the code it describes still looks the way it did at capture time. The prior design note's Consequences section already names this gap: "Age-based decay can suppress old context but cannot recognize a repository revision; Git/file fingerprints ... remain provider opportunities." A stale-looking but still-accurate node is discarded for no reason, and a fresh-looking but since-rewritten node is injected as if it were still true — the second failure mode is the dangerous one, because an agent has no way to tell a confidently wrong checkpoint from a correct one.

Replacing age with a full re-derivation (re-run the whole trajectory) is not viable: it would spend the tokens the feature exists to save. The alternative is to check whether the specific facts a checkpoint depends on — the files, symbols, and command outputs its trajectory actually read — still hold, without another model call.

## Decision

Split a checkpoint into three parts with independent invalidation speed: identity/matching fields (unchanged), structured conclusions plus a separate dead-ends field, and a new **replay checklist** — an ordered list of no-model-call probes recorded at capture time. Each probe records `{ seq, kind, path, capturedFingerprint, loadBearing }`. `loadBearing` is set by a cheap write-time heuristic (did this probe's output feed a later tool argument, a subsequently-edited file's last read, or the final conclusion text); only load-bearing probes count toward the freshness prefix, so an incidental drift (an added comment, an unrelated line) cannot invalidate a node whose actual dependency still holds.

Replay runs in confidence tiers, not a generic diff: `path-exists` and `file-hash` are exact (L0); `grep` presence (a symbol still appears somewhere in the file; line-number shift is not a failure) is structural (L1). Both participate in the verdict. A tier for scrubbed command stdout (L2) is deliberately deferred — it needs a noise baseline first (see Verification) before it can safely participate.

The verdict is a longest-consistent-prefix computation: `k` is how many load-bearing probes, in `seq` order, replay consistently before the first inconsistency; `n` is the total load-bearing probe count. `k === n` with the recorded touched paths mostly covering what changed since capture (`scopeRatio`, see below) is `fresh`; a large-enough consistent prefix is `partial`; a small prefix whose paths still exist is `locational`; every probe fingerprinting to `missing` is `dead`. `scopeRatio` is a coarse guard against the blind spot where the codebase changed substantially but happened not to touch anything the checkpoint's probes read: it downgrades an otherwise-full pass rather than trusting it unconditionally. `computeScopeRatio` reads `git diff --name-only <capturedHead>` against the live working tree (not a clean checkout of `HEAD`), because uncommitted changes are exactly the state a forked agent will actually face.

This first slice (`packages/context/context-graph/src/replay.ts`) implements only the no-sandbox probes above (`path-exists`, `file-hash`, `grep`) — what the design spec calls Phase 1. Phase 2 (copy-on-write sandboxed re-execution of exec probes, gated on Phase 1 passing) is not implemented here; a checkpoint with only Phase 1 probes already produces a real verdict without it.

`replayChecklist` never throws: a replay-infrastructure failure — most concretely, the captured commit no longer resolving because history was pruned, rebased, or the checkout is shallow — reports `dead` rather than propagating an exception. This is deliberate, not defensive-programming reflex: environment drift of that kind is itself a strong freshness signal, not an error state the caller should have to guard against separately.

`computeScopeRatio` restricts its diff to the touched paths' containing directories, not the whole `cwd`. This was not the first cut: `scripts/replay-decay-eval.ts` replays real historical checkpoints of this repository's own `packages/core/session/src/types.ts` against its own subsequent commits, and with an unrestricted repo-wide diff the scope guard downgraded every single sample away from `fresh` — including one commit after capture — because in an active 248-project monorepo, unrelated activity elsewhere always swamps a denominator sized to the whole tree. Directory-scoping produced the actually-decaying curve (50% still `fresh` one commit later, 14% by ten commits later) that a coarse conservative guard is supposed to produce. This is the kind of thing the small synthetic repos in `tests/replay.spec.ts` cannot surface — they are single-directory by construction, so the bug was invisible until measured against a real multi-project tree.

## Alternatives considered

**Keep age-based freshness and only add manual staleness marking.** Rejected because it depends on a person noticing drift; the design goal is a check that runs for free on every candidate.

**Treat any probe drift as invalidating.** Rejected: an unrelated comment or reformatted neighboring line would kill a node whose actual dependency is untouched, which is a bigger practical cost than a slightly more permissive verdict. The load-bearing/non-load-bearing split exists specifically to avoid this false-positive class.

**Compare `HEAD` at replay time instead of the working tree.** Rejected because a fork inherits the user's actual uncommitted state, not a clean checkout; validating against `HEAD` would validate a world the forked agent will not be in.

**Let every probe kind participate in the verdict, including raw command stdout.** Rejected until a scrubber's noise floor is measured (Layer 0 below); unscrubbed non-determinism would make the verdict noisier than the thing it replaces.

## Verification

`packages/context/context-graph/tests/replay.spec.ts` covers the two layers that can run before any model call or paired online trial: a noise baseline (replaying an unchanged commit twenty times, and replaying the same commit from an independent clone, both asserting an identical `fresh` verdict) and verifier accuracy against real git history used as ground truth (a real commit that only touches recorded paths stays `fresh`; an unrecorded-path change downgrades a full pass to `partial` through the scope guard; drift confined to a non-load-bearing probe is ignored; a real content change past a given probe produces the exact expected `k`/`partial`; a broken prefix over a still-present path is `locational`; a deleted path is `dead`). All of it runs against real temporary git repositories rather than mocks, because the verifier's premise is that it observes the actual working tree.

`scripts/replay-decay-eval.ts` goes further than the synthetic tests: it derives probes automatically from a real file's exported symbols (a small regex-based stand-in for the write-side capture step this note's Decision section says is still unbuilt) at several real historical commits, then replays them against this repository's own subsequent history through real `git worktree` checkouts. Run against `packages/core/session/src/types.ts` (152 commits, 58 days of active history), the median time to the first symbol-level break across 8 sampled capture points was 27.8 days, with two of eight still holding at the end of their sampled window — a first real half-life estimate for this codebase, not the 30-day constant the age-based baseline currently guesses. This script is also what surfaced the `computeScopeRatio` directory-scoping bug described above.

`scripts/build-layer2-taskset.ts` builds the task side of Layer 2 the same way: real commits from this repository's own history, not synthetic or borrowed ones. For each commit that pairs a source change with a test change in one package, it doesn't trust the commit message — it temporarily rewrites the working tree to the parent's source plus the new commit's test (expecting the test to fail, RED) and then to the new commit's source (expecting it to pass, GREEN), restoring every touched file immediately after regardless of outcome. It also checks PASS_TO_PASS (SWE-bench's term): after GREEN, the package's whole test directory, not just the targeted spec file, must still pass — a fix that quietly breaks something else nearby isn't a task worth keeping. Scanning 216 packages found 887 structurally-qualifying commits; sampling 150 of them (deterministic shuffle) and validating each against the real test suite accepted 15. 124 were rejected because the commit's own change wasn't sufficient in isolation to reach GREEN (usually a sign the real fix also touched a file outside the single package this tool considers, an honest scope limit rather than a bug), 6 because the parent's code already satisfied the new test, and 5 by the PASS_TO_PASS check catching a regression the narrow check alone would have missed. Both scripts leave the working tree exactly as they found it; `build-layer2-taskset.ts` refuses to run at all against a working tree with uncommitted changes to tracked files.

`scripts/build-context-pairs.ts` adds the structure the six-arm trial actually needs on top of this: SWE-ContextBench (arXiv:2602.08316) found that existing benchmarks treat every task as independent and don't test whether an agent can reuse prior experience across related ones, and built a base+related task-pair dataset for exactly that. This script does the same against `layer2-taskset.json` — for each validated task, it looks back (deliberately *nearest prior touch only*, not all commits in the window: an earlier draft that paired every commit against every other commit sharing a file produced 133,075 pairs from combinatorial explosion on frequently-touched files, which is useless as a task set) for the closest earlier commit touching one of the same source files, within a 30-day window chosen to match the ~27.8-day half-life `replay-decay-eval.ts` measured. All 15 validated tasks found a qualifying prior commit; most were same-day (the immediately preceding feature/refactor commit that introduced what the fix then corrected), a few 5-10 days out. This is the actual A/B/D-arm material: a base checkpoint, and a later task that a recall system could plausibly help with.

Not yet built: the paired six-arm cost/quality trial and the shadow-mode online loop from the full design spec are gated on this verifier layer holding up on a real project's commit history first — they are expensive, and an inaccurate verifier makes their result meaningless. The 15-task, 15-pair set above is sized for a pilot of that trial, not the full thing; scaling it further just means sampling more of the same 887 candidates. What it still lacks relative to the mature open-source tooling it borrows from: a decontamination check (GitBug-Java's approach — restrict mining to commits after a model's training cutoff — doesn't apply the same way to a private monorepo a public model never saw, but a model fine-tuned on this org's own history would need it) and difficulty grading.

**A/D pilot, n=1×3 (`scripts/run-layer2-pilot.ts`), against a real model (`deepseek-v4-flash`):** four attempts were needed to get a trustworthy read, and the debugging path is itself worth recording. The first attempt (4000-token cap) truncated 4 of 6 calls. Raising the cap to 8000, then 32000, didn't help — at 32000 two tasks still hit `finish_reason: "length"` with a **completely empty visible `content` field**: every one of those 32000 completion tokens had gone into this model's default "thinking mode," whose chain-of-thought is billed as completion tokens but returned in a separate `reasoning_content` field this script wasn't reading (DeepSeek's [thinking-mode docs](https://api-docs.deepseek.com/guides/thinking_mode/)). A bigger cap only gives invisible reasoning more room to run; it was never going to reach the actual answer sooner. Passing `thinking: { type: "disabled" }` fixed it outright — the fourth attempt hit `finish_reason: "stop"` on all 6 calls, with sensible 1.5k-3.8k-token outputs.

With truncation actually gone, the real picture: two of the three tasks fail for a legitimate reason — the model returns a complete, well-formed file that simply doesn't fix the bug (checked directly: the returned code is syntactically whole, not cut off), a genuine capability limit of a fast/cheap model on subtler fixes, not a harness defect. The third task (`760bc9aa`, `util/timeout`) passed on both arms, but its arm-D-vs-arm-A token delta came out **different every single time across the first three configurations** — net saving, then net cost, then a smaller net cost — despite `temperature: 0` on identical inputs. At the time this read as the design spec's own Layer 2 statistical warning ("agent 方差很大，n=1 的对比是噪声") playing out live.

**It wasn't, quite — and the correction matters.** Re-running the same three tasks `TRIALS=10` times each under one *fixed* configuration (thinking disabled, max_tokens 16000) rather than changing the setup between single-shot attempts, as the earlier runs had: the outputs came back **nearly deterministic**. Two tasks produced byte-identical token counts across all 10 trials in both arms (`87f4e0b2`: 5587/6126 every time; `8f5c592b`: 12135-12162/12677-12781, a ≤1% spread); the third (`760bc9aa`) varied by only ~5% (5821-6120 for A, 6340-6362 for D). The earlier "different sign every run" was not inherent model stochasticity — it was an artifact of comparing runs made under *different* token caps and thinking-mode settings, which is not a controlled comparison at all. Once genuinely controlled, the answer stopped moving around.

And the controlled answer is clear, consistent, and unhelpful to the token-saving hypothesis: **arm D cost more than arm A on all three tasks**, every single trial — median deltas of −539, −507, and −598 tokens (negative = D more expensive), driven by the ~500-600 extra input tokens the recall block itself costs, with no compensating drop in output length. Where D did help was a different axis entirely: `760bc9aa`'s success rate went from 90% (9/10) to 100% (10/10) with recall injected — a real, if small-sample, reliability signal, separate from and orthogonal to the cost question, exactly the kind of split result the design spec's six-arm framing exists to keep from collapsing into one misleading number. Total cost for all 60 calls: ¥0.57 (checked via `/user/balance` before and after). The harness itself also had one real bug on the very first attempt (`return run()` instead of `return await run()` let the file-restore `finally` fire before the async model call and file rewrite it was supposed to wrap, leaving six files dirty; fixed and reverified clean on every subsequent run, including this one).

None of this generalizes past "one flash-tier model, three small single-file tasks, one specific recall-block format." What it does establish: the harness is now trustworthy end to end (real oracle, no truncation, verified-clean restores, checked spend), and the single biggest lesson for running this at any larger scale is to **hold the model configuration fixed across all trials being compared** — the apparent noise in the first three attempts was experimental-design noise, not the "agent variance" the design spec was warning about, and conflating the two would have been the wrong conclusion to draw.

## Consequences

A checkpoint can now report a specific, falsifiable reason to trust or distrust it, instead of only its age. The load-bearing distinction and the scope-ratio guard are both intentionally coarse, conservative heuristics rather than a proof of correctness: `scopeRatio` in particular will downgrade some checkpoints that are actually still fine whenever unrelated files move without being listed as touched, trading recall for a lower false-`fresh` rate. Phase 2 (sandboxed exec-probe replay) and the L2 confidence tier remain open work, as does wiring this verdict into `graph.ts`'s node projection and the recall-injection path in `index.ts` — this note covers the probe/verdict primitive and its own test layer, not yet its integration into automatic recall.
