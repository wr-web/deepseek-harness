# Agent Note: Replay-verified checkpoint freshness for the context graph

Status: proposed

English | [中文](2026-09-05-context-graph-replay-verification.zh.md)

## Problem

`@deepseek-ai/dsh-context-graph`'s freshness classification (`fresh`/`aging`/`stale` in `src/graph.ts`) is purely age-based: a node younger than half its configured lifetime is `fresh` regardless of whether the code it describes still looks the way it did at capture time. The prior design note's Consequences section already names this gap: "Age-based decay can suppress old context but cannot recognize a repository revision; Git/file fingerprints ... remain provider opportunities." A stale-looking but still-accurate node is discarded for no reason, and a fresh-looking but since-rewritten node is injected as if it were still true — the second failure mode is the dangerous one, because an agent has no way to tell a confidently wrong checkpoint from a correct one.

Replacing age with a full re-derivation (re-run the whole trajectory) is not viable: it would spend the tokens the feature exists to save. The alternative is to check whether the specific facts a checkpoint depends on — the files, symbols, and command outputs its trajectory actually read — still hold, without another model call.

## Decision

Split a checkpoint into three parts with independent invalidation speed: identity/matching fields (unchanged), structured conclusions plus a separate dead-ends field, and a new **replay checklist** — an ordered list of no-model-call probes recorded at capture time. Each probe records `{ seq, kind, path, capturedFingerprint, loadBearing }`. `loadBearing` is set by a cheap write-time heuristic (did this probe's output feed a later tool argument, a subsequently-edited file's last read, or the final conclusion text); only load-bearing probes count toward the freshness prefix, so an incidental drift (an added comment, an unrelated line) cannot invalidate a node whose actual dependency still holds.

Replay runs in confidence tiers, not a generic diff: `path-exists` and `file-hash` are exact (L0); `grep` presence (a symbol still appears somewhere in the file; line-number shift is not a failure) is structural (L1). Both participate in the verdict. A tier for scrubbed command stdout (L2) is deliberately deferred — it needs a noise baseline first (see Verification) before it can safely participate.

The verdict is a longest-consistent-prefix computation: `k` is how many load-bearing probes, in `seq` order, replay consistently before the first inconsistency; `n` is the total load-bearing probe count. `k === n` with the recorded touched paths mostly covering what changed since capture (`scopeRatio`, see below) is `fresh`; a large-enough consistent prefix is `partial`; a small prefix whose paths still exist is `locational`; every probe fingerprinting to `missing` is `dead`. `scopeRatio` is a coarse guard against the blind spot where the codebase changed substantially but happened not to touch anything the checkpoint's probes read: it downgrades an otherwise-full pass rather than trusting it unconditionally. `computeScopeRatio` reads `git diff --name-only <capturedHead>` against the live working tree (not a clean checkout of `HEAD`), because uncommitted changes are exactly the state a forked agent will actually face.

This first slice (`packages/context/context-graph/src/replay.ts`) implements only the no-sandbox probes above (`path-exists`, `file-hash`, `grep`) — what the design spec calls Phase 1. Phase 2 (copy-on-write sandboxed re-execution of exec probes, gated on Phase 1 passing) is not implemented here; a checkpoint with only Phase 1 probes already produces a real verdict without it.

`replayChecklist` never throws: a replay-infrastructure failure — most concretely, the captured commit no longer resolving because history was pruned, rebased, or the checkout is shallow — reports `dead` rather than propagating an exception. This is deliberate, not defensive-programming reflex: environment drift of that kind is itself a strong freshness signal, not an error state the caller should have to guard against separately.

`computeScopeRatio` restricts its diff to the touched paths' containing directories, not the whole `cwd`. This was not the first cut: `scripts/replay-decay-eval.ts` replays real historical checkpoints of this repository's own `packages/core/session/src/types.ts` against its own subsequent commits, and with an unrestricted repo-wide diff the scope guard downgraded every single sample away from `fresh` — including one commit after capture — because in an active 248-project monorepo, unrelated activity elsewhere always swamps a denominator sized to the whole tree. Directory-scoping produced the actually-decaying curve (50% still `fresh` one commit later, 14% by ten commits later) that a coarse conservative guard is supposed to produce. This is the kind of thing the small synthetic repos in `tests/replay.spec.ts` cannot surface — they are single-directory by construction, so the bug was invisible until measured against a real multi-project tree.

## Alternatives considered

**Keep age-based freshness and only add manual staleness marking.** Rejected because it depends on a person noticing drift; the design goal is a check that runs for free on every candidate.

**Treat any probe drift as invalidating.** Rejected: an unrelated comment or reformatted neighboring line would kill a node whose actual dependency is untouched, which is a bigger practical cost than a slightly more permissive verdict. The load-bearing/non-load-bearing split exists specifically to avoid this false-positive class.

**Compare `HEAD` at replay time instead of the working tree.** Rejected because a fork inherits the user's actual uncommitted state, not a clean checkout; validating against `HEAD` would validate a world the forked agent will not be in.

**Let every probe kind participate in the verdict, including raw command stdout.** Rejected until a scrubber's noise floor is measured (Layer 0 below); unscrubbed non-determinism would make the verdict noisier than the thing it replaces.

## Verification

`packages/context/context-graph/tests/replay.spec.ts` covers the two layers that can run before any model call or paired online trial: a noise baseline (replaying an unchanged commit twenty times, and replaying the same commit from an independent clone, both asserting an identical `fresh` verdict) and verifier accuracy against real git history used as ground truth (a real commit that only touches recorded paths stays `fresh`; an unrecorded-path change downgrades a full pass to `partial` through the scope guard; drift confined to a non-load-bearing probe is ignored; a real content change past a given probe produces the exact expected `k`/`partial`; a broken prefix over a still-present path is `locational`; a deleted path is `dead`). All of it runs against real temporary git repositories rather than mocks, because the verifier's premise is that it observes the actual working tree.

`scripts/replay-decay-eval.ts` goes further than the synthetic tests: it derives probes automatically from a real file's exported symbols (a small regex-based stand-in for the write-side capture step this note's Decision section says is still unbuilt) at several real historical commits, then replays them against this repository's own subsequent history through real `git worktree` checkouts. Run against `packages/core/session/src/types.ts` (152 commits, 58 days of active history), the median time to the first symbol-level break across 8 sampled capture points was 27.8 days, with two of eight still holding at the end of their sampled window — a first real half-life estimate for this codebase, not the 30-day constant the age-based baseline currently guesses. This script is also what surfaced the `computeScopeRatio` directory-scoping bug described above.

`scripts/build-layer2-taskset.ts` builds the task side of Layer 2 the same way: real commits from this repository's own history, not synthetic or borrowed ones. For each commit that pairs a source change with a test change in one package, it doesn't trust the commit message — it temporarily rewrites the working tree to the parent's source plus the new commit's test (expecting the test to fail, RED) and then to the new commit's source (expecting it to pass, GREEN), restoring every touched file immediately after regardless of outcome. It also checks PASS_TO_PASS (SWE-bench's term): after GREEN, the package's whole test directory, not just the targeted spec file, must still pass — a fix that quietly breaks something else nearby isn't a task worth keeping. Scanning 216 packages found 887 structurally-qualifying commits. An initial 150-candidate sample accepted 15; widening to 400 candidates accepted 38 across many more packages. 326 of the 400 were rejected because the commit's own change wasn't sufficient in isolation to reach GREEN (usually a sign the real fix also touched a file outside the single package this tool considers, an honest scope limit rather than a bug), 21 because the parent's code already satisfied the new test, and 15 by the PASS_TO_PASS check catching a regression the narrow check alone would have missed. Both scripts leave the working tree exactly as they found it; `build-layer2-taskset.ts` refuses to run at all against a working tree with uncommitted changes to tracked files.

`scripts/build-context-pairs.ts` adds the structure the six-arm trial actually needs on top of this: SWE-ContextBench (arXiv:2602.08316) found that existing benchmarks treat every task as independent and don't test whether an agent can reuse prior experience across related ones, and built a base+related task-pair dataset for exactly that. This script does the same against `layer2-taskset.json` — for each validated task, it looks back (deliberately *nearest prior touch only*, not all commits in the window: an earlier draft that paired every commit against every other commit sharing a file produced 133,075 pairs from combinatorial explosion on frequently-touched files, which is useless as a task set) for the closest earlier commit touching one of the same source files, within a 30-day window chosen to match the ~27.8-day half-life `replay-decay-eval.ts` measured. All 38 validated tasks found a qualifying prior commit; most were same-day (the immediately preceding feature/refactor commit that introduced what the fix then corrected), a few 5-10 days out. This is the actual A/B/D-arm material: a base checkpoint, and a later task that a recall system could plausibly help with.

Not yet built: the shadow-mode online loop from the full design spec is gated on the six-arm trial itself being informative first. What it still lacks relative to the mature open-source tooling it borrows from: a decontamination check (GitBug-Java's approach — restrict mining to commits after a model's training cutoff — doesn't apply the same way to a private monorepo a public model never saw, but a model fine-tuned on this org's own history would need it), difficulty grading, and (see below) a way to test the specific hypothesis "does recall help more once a project has accumulated more history" rather than just "does the nearest one prior commit help."

**A/D pilot, n=1×3 (`scripts/run-layer2-pilot.ts`), against a real model (`deepseek-v4-flash`):** four attempts were needed to get a trustworthy read, and the debugging path is itself worth recording. The first attempt (4000-token cap) truncated 4 of 6 calls. Raising the cap to 8000, then 32000, didn't help — at 32000 two tasks still hit `finish_reason: "length"` with a **completely empty visible `content` field**: every one of those 32000 completion tokens had gone into this model's default "thinking mode," whose chain-of-thought is billed as completion tokens but returned in a separate `reasoning_content` field this script wasn't reading (DeepSeek's [thinking-mode docs](https://api-docs.deepseek.com/guides/thinking_mode/)). A bigger cap only gives invisible reasoning more room to run; it was never going to reach the actual answer sooner. Passing `thinking: { type: "disabled" }` fixed it outright — the fourth attempt hit `finish_reason: "stop"` on all 6 calls, with sensible 1.5k-3.8k-token outputs.

With truncation actually gone, the real picture: two of the three tasks fail for a legitimate reason — the model returns a complete, well-formed file that simply doesn't fix the bug (checked directly: the returned code is syntactically whole, not cut off), a genuine capability limit of a fast/cheap model on subtler fixes, not a harness defect. The third task (`760bc9aa`, `util/timeout`) passed on both arms, but its arm-D-vs-arm-A token delta came out **different every single time across the first three configurations** — net saving, then net cost, then a smaller net cost — despite `temperature: 0` on identical inputs. At the time this read as the design spec's own Layer 2 statistical warning ("agent 方差很大，n=1 的对比是噪声") playing out live.

**It wasn't, quite — and the correction matters.** Re-running the same three tasks `TRIALS=10` times each under one *fixed* configuration (thinking disabled, max_tokens 16000) rather than changing the setup between single-shot attempts, as the earlier runs had: the outputs came back **nearly deterministic**. Two tasks produced byte-identical token counts across all 10 trials in both arms (`87f4e0b2`: 5587/6126 every time; `8f5c592b`: 12135-12162/12677-12781, a ≤1% spread); the third (`760bc9aa`) varied by only ~5% (5821-6120 for A, 6340-6362 for D). The earlier "different sign every run" was not inherent model stochasticity — it was an artifact of comparing runs made under *different* token caps and thinking-mode settings, which is not a controlled comparison at all. Once genuinely controlled, the answer stopped moving around.

And the controlled answer is clear, consistent, and unhelpful to the token-saving hypothesis: **arm D cost more than arm A on all three tasks**, every single trial — median deltas of −539, −507, and −598 tokens (negative = D more expensive), driven by the ~500-600 extra input tokens the recall block itself costs, with no compensating drop in output length. Where D did help was a different axis entirely: `760bc9aa`'s success rate went from 90% (9/10) to 100% (10/10) with recall injected — a real, if small-sample, reliability signal, separate from and orthogonal to the cost question, exactly the kind of split result the design spec's six-arm framing exists to keep from collapsing into one misleading number. Total cost for all 60 calls: ¥0.57 (checked via `/user/balance` before and after). The harness itself also had one real bug on the very first attempt (`return run()` instead of `return await run()` let the file-restore `finally` fire before the async model call and file rewrite it was supposed to wrap, leaving six files dirty; fixed and reverified clean on every subsequent run, including this one).

None of the 3-task result generalizes past "one flash-tier model, three small single-file tasks, one specific recall-block format." What it did establish: the harness is trustworthy end to end (real oracle, no truncation, verified-clean restores, checked spend), and the single biggest lesson for running it at any larger scale is to **hold the model configuration fixed across all trials being compared** — the apparent noise in the first three attempts was experimental-design noise, not the "agent variance" the design spec was warning about, and conflating the two would have been the wrong conclusion to draw.

**Scaling to 34 tasks × 2 arms × 5 trials (340 calls) confirms the direction and adds a second, more interesting negative result.** `run-layer2-pilot.ts` no longer hardcodes 3 commits — it runs every single-source/single-test-file task with a pairing (34 of the 38 in the widened task set), motivated by the hypothesis that repeated development on the same project might make recall pay off *more* as a codebase accumulates history, which a 3-task sample cannot speak to at all. The result: **every one of the 34 tasks** showed arm D costing more than arm A, at every trial, with no exceptions — median deltas from −200 to −695 tokens, overall median −537.5. Bucketing by how recent the paired prior commit was (`<1d`: 26 tasks, median −540; `1-7d`: 5 tasks, median −437; `≥7d`: 3 tasks, median −336) shows the cost shrinking slightly as the prior commit gets older, but with 3-5 tasks in the sparser buckets this is not a claim worth leaning on — it is reported because it is the opposite of what "more relevant, more recent context helps more" would predict, not because it is statistically solid.

Success rate moved the *other* direction from the 3-task pilot's positive signal: overall, A succeeded 35.9% of trials and D succeeded 31.8% — recall made things slightly worse on average, not better, once measured across enough tasks that one lucky task can't set the story. Most tasks were unaffected (A and D succeeded or failed at the same rate); a few flipped in each direction (`698fdaea` went 100%→0%, `acc628f3` 40%→0%, `600f3a31` 100%→80% with recall; `ca119b0e` went 80%→100%). Total cost for 340 calls: ¥7.63 (balance ¥13.84 → ¥6.21) — markedly more per call than the earlier 60-call run's ¥0.0095/call average, because the widened task pool pulled in several much larger files (`py-types.ts` at 818 lines, `protocol.ts` at 656) whose full-file-rewrite prompts run 15,000-48,000 tokens each, not the ~250-line files' 5,000-12,000.

**What this does and doesn't settle.** It's now a well-powered negative result for the specific thing tested: injecting the single temporally-nearest same-file prior commit, formatted as a truncated raw diff, into a flash-tier model asked to rewrite a whole file, does not save tokens and does not reliably improve correctness, across 34 real, diverse tasks. It does *not* test the hypothesis that motivated this scale-up — "does recall help more after many rounds of development on the same project" is a claim about *accumulated* history (many candidate checkpoints to choose from, picked by relevance) that this design can't speak to, because it always injects exactly one candidate (the nearest in time), never a richer pool the way the real `matchContextGraph` lexical ranking would. It **also** does not test the design's actual value proposition at all: every task above handed the model the exact failing test and exact source file directly. There is no exploration to save when the answer's location is given away in the prompt — of course an extra injected paragraph can only add cost in that setup.

**`run-layer2-exploration-pilot.ts` tests the real claim: does recall save exploration.** A real multi-turn tool-calling agent (`list_directory`, `read_file`, `search_code`, `submit_fix`) is dropped into the task's package with only a commit-message-level description — never the file path or test content — and must find its own way to the bug, the way a fresh session actually would. Arm D prepends the same "Reused context checkpoint" block before the agent's first turn, exactly like `index.ts`'s real `recallForFirstTurn`. Every tracked file in the package is snapshotted and restored regardless of which file the agent's `submit_fix` actually touches, since it might explore its way to the wrong one.

Two smoke-test bugs surfaced before the real run was trustworthy, both fixed and reverified: `resolveWithinPackage` rejected an empty relative path, which is exactly what a request for the package root (`.`) resolves to — the agent's very first `list_directory('.')` was silently failing every time, so it never got anywhere. And a "refactor" task (cross-package Remote-wiring plumbing) sent the agent hunting through `node_modules` for a symbol definition, burning ~100k tokens without converging — fixed by excluding `node_modules` from all three read tools and restricting task selection to `fix(...)`-scoped commits, which are far more likely to live in one findable place than a refactor is.

**The real run (8 tasks × 2 arms × 3 trials = 48 sessions) landed on something more fundamental than a cost number.** Success rate: **0% in both arms, all 48 sessions.** This flash-tier model essentially cannot do real explore-then-fix at all — even the handful of sessions that did call `submit_fix` produced a fix that still failed the oracle. That makes the success-rate half of the hypothesis untestable with this model: there is no signal to compare when neither arm ever succeeds. The cost half is still measurable, and it came back unambiguous: **every one of the 8 tasks** showed arm D using more tokens *and* more turns than arm A (overall median turns 5 vs. 7, tokens −11,553) — recall didn't shorten exploration, it lengthened it, the opposite of the hypothesis, with zero compensating success-rate benefit to weigh against that cost.

**Trying a stronger model (`deepseek-v4-pro`) to give the success-rate question a fair shot found a real tooling bug before it found an answer.** A 2-task smoke test showed the model exploring sensibly (landing on the actually-correct file) but running out of its tool-call budget before ever reaching `submit_fix` — raising the cap to 20 tool calls / 18 turns and running the full 8×2×2 design (32 sessions) surfaced `git grep` fatal errors ("Unmatched ( or \(") on a large share of the model's own search queries: patterns like `it(`, `describe(`, or `isJsonValue(value[i]` are exactly the kind of literal code snippet a model naturally searches for, and none of them are valid extended regex. `search_code` was silently handing the model a broken tool for a large share of realistic queries, not a fair test of its exploration. Fixed by falling back to a fixed-string search (`-F`) on a regex parse failure.

**Re-running the identical 8×2×2 design with the fix made no difference to success, and confirmed the earlier bug wasn't the bottleneck: still 0% in both arms, both pro-model runs (64 sessions total).** Even a substantially more capable model, given a generous exploration budget and a working search tool, cannot reliably land a correct fix from a bare commit-message-level description in this repository. That itself is a finding worth keeping: this task framing (cold multi-package repo, minimal prompt, small tool surface) is hard enough that model tier alone didn't clear it — twice.

The cost picture, though, came out differently for the stronger model than for flash, and consistently so across both pro runs: where flash showed arm D costing *more* on every single task with no exceptions, pro showed arm D costing *less* on 5 of 8 tasks in both runs (overall median tokens saved: +14,011 in the buggy-search run, +20,930 after the fix), with the identity of which 5 tasks shifting somewhat between runs. Read cautiously — n=2 per arm, and every one of these sessions still ended in failure, so this is "cost of a failed attempt," not "cost of a successful fix" — but the direction is a real, replicated difference from flash's finding, and a plausible reading is that a stronger model can partly use injected context to cut short exploration it would otherwise have done, even when that context isn't enough to get all the way to a correct answer. That is a materially different and more interesting result than "recall never helps," and it's the opposite of what the flash-model result would have predicted if extrapolated to a better model.

Total cost across the whole exploration-cost investigation: ¥0.47 (flash, 48 sessions) + ¥2.78 (pro, 32 sessions, buggy search) + ¥2.36 (pro, 32 sessions, fixed search) = **¥5.61** for 112 real multi-turn agentic sessions (balance ¥26.09 → ¥20.15). Model capability and task framing, not budget, are the binding constraints on pushing this further: the natural next step is a task set (or a repo) where a strong model can actually *succeed* some of the time, so the success-rate half of the hypothesis has a chance to show a signal at all — not just its cost half.

**Correction: every "0%" result above is invalid. The oracle itself was broken, not the model.** `runVitestResult`/`runVitestExitCode` in `run-layer2-exploration-pilot.ts` ran vitest relative to `packageDir`. This is a 216-package pnpm workspace where individual packages do not carry their own `node_modules/vitest` — only the monorepo root's `node_modules` does. Every `submit_fix` call across all 144 sessions summarized above (48 flash + 64 pro) ran an oracle check against a module path that could never resolve, which fails shut: it reports FAIL regardless of whether the model's fix was actually correct. This means the entire "0% in both arms" finding, the flash cost comparison, and the pro cost comparison above all measured *the cost of a session whose success could never be observed*, not the cost of real attempts at a real oracle. The bug was caught by behavioral evidence, not a passing test: an agent transcript showed the model inspecting `package.json` and `node_modules` immediately after calling `submit_fix`, the pattern of a model reacting to a dependency-resolution error rather than a semantic test failure — which is exactly what a broken `require`/module-resolution path looks like from the model's side. Fixed by threading `repoRoot` through `runSession()` and calling `runVitestResult(repoRoot, task.testFiles)` with repo-relative paths run from the workspace root — the same pattern `run-layer2-pilot.ts` already used correctly. A 3-task/1-trial flash smoke test immediately after the fix produced a genuine PASS (`6cbf927e`, 5 turns, 1 `submit_fix` attempt, 19,562 tokens) — the first real success in the entire exploration-cost investigation, confirming both that the bug was real and that the fix works.

**Re-running flash at the full 8×2×5 design (80 sessions) with the fixed oracle: success is now real, small, and statistically indistinguishable between arms; cost still favors no-recall overall, but the pooled number hides two opposite task-level effects.** Arm A: 7.5% success (3/40), median 27,819 tokens, median 8 turns. Arm D: 10.0% success (4/40), median 39,161 tokens, median 8 turns. A two-sided Fisher exact test on the 3-vs-4 successes gives p=1.0 — no directional signal at this sample size. Pairing each arm-A session against the same task and trial index in arm D and taking the token difference (n=40 pairs): median −4,833 (negative = D more expensive), and D was the cheaper arm in only 9 of 40 pairs. The extra cost concentrates in cached-input tokens (median 31,360 for D vs. 24,320 for A) — the recall block itself, not a longer output — so this reproduces the single-shot pilot's earlier finding that the injected block is a fixed cost the model doesn't reliably recoup. The task-level split is the more interesting result: on `6cbf927e`, arm D succeeded on 3 of 5 trials while arm A succeeded on 0 of 5 — recall was decisive. On `600f3a31`, the opposite: arm A succeeded on 3 of 5 while arm D succeeded on only 1 of 5 — recall actively hurt. These two effects largely cancel in the pooled 7.5%-vs-10.0% number, which is exactly the failure mode the design spec's multi-arm framing exists to catch: a single aggregate statistic would have reported "no effect" while hiding two real, opposite, task-specific effects underneath it.

**Pro-tier re-run with the fixed oracle (8 tasks × 2 arms × 3 trials = 48 sessions, matched to flash's turn/tool-call budget for a fair comparison): a directionally larger recall effect than flash showed, still short of significance at this n.** Arm A: 4.2% success (1/24), median 44,649 tokens, median 10 turns. Arm D: 12.5% success (3/24), median 46,401 tokens, median 9 turns — 3x the success rate, but a two-sided Fisher exact test on 1-vs-3 successes still gives p=0.61 (too few events to separate from noise). Overall token cost is close to a wash (paired median +1,511 tokens favoring D, mean −3,070 favoring A — the median/mean disagreement itself says the distribution is skewed by a couple of large outliers rather than a clean effect either way; D was the cheaper arm in 13 of 24 pairs, A in 11). Pooling both model tiers (40 flash + 24 pro = 64 sessions per arm): A 6.25% (4/64), D 10.9% (7/64), combined Fisher p=0.53 — a consistent ~1.7-3x directional signal in both tiers individually and pooled, but never reaching significance at this sample size.

**The same task, `6cbf927e`, replicates the identical decisive effect in both model tiers — this is the strongest single finding of the whole investigation.** Flash: D succeeded 3/5 trials, A succeeded 0/5. Pro: D succeeded 3/3 trials, A succeeded 0/3. Across both models, six D-arm trials on this task succeeded and zero failed; eight A-arm trials and zero succeeded. Reading the tool-call logs explains why: the recall block names the actual file (`src/startup.ts`) and the relevant test up front, so arm D's agent goes `list_directory` → one targeted `search_code` → straight to `read_file` on the two right files → `submit_fix`, converging in 5-7 turns. Arm A's agent, with no such lead, spends its budget checking a plausible-but-wrong directory (`lib`), re-reading `src/index.ts` twice, and grepping for terms that don't appear in the right file — and in every single traced case runs out of its turn budget before ever calling `submit_fix`. This is the exploration-cost hypothesis working exactly as designed: a checkpoint that names the right file turns a budget-exhausting search into a five-turn conversation.

**Task `daaede29` replicates the opposite pattern in both tiers, and is just as informative.** Flash: D cost 14,731 more median tokens than A. Pro: D cost 41,720 more. Neither arm ever succeeded on this task in either model. The recall block here also correctly names the right file (`turn-error.ts`) and test — arm D's agent does land on it immediately, the same as `6cbf927e` — but then gets stuck: the pro-tier trace shows it re-reading the *same* 120-line offset of the test file twice, followed by three separate greps trying to pin down one exact assertion, burning its entire tool-call budget re-verifying a file it had already found rather than converging on a fix. Arm A, searching blind, spends a comparable budget but on genuinely different exploration (never finds the file, but also never gets stuck re-reading it). The lesson: correctly narrowing *where* to look doesn't guarantee the agent converges faster — a checkpoint can point at the right file and the model can still spend its whole budget second-guessing that same file instead of acting on it. Recall shortens exploration only when the model actually trusts and acts on what it's given; when it doesn't, the extra context is pure overhead with no offsetting benefit.

**Total cost for the oracle-fixed re-runs: ¥2.71 for 131 sessions (¥19.00 → ¥16.29): 3 flash smoke-test sessions + 80 flash sessions (¥0.85) + 48 pro sessions (¥1.86).** Combined with the ¥5.61 spent on the pre-fix (now-invalid) runs, the whole exploration-cost investigation to date has cost ¥8.32 across 243 real multi-turn agentic sessions.

**Where this leaves the hypothesis.** "Recall saves exploration cost" is not supported in aggregate at either model tier — the pooled token and success-rate numbers are statistically indistinguishable between arms, at n's too small to rule out a real but modest effect either way. But the hypothesis isn't simply false, either: it is real, large, and consistent on a task where the checkpoint correctly names the file *and* the model acts on that information (`6cbf927e`, replicated across two model tiers, six-for-six vs zero-for-eight), and it is real, large, and *negative* on a task where the checkpoint names the file correctly but the model doesn't trust it enough to skip re-verifying (`daaede29`, also replicated). The aggregate near-zero effect is an average over these two real, opposite, task-dependent effects, not evidence that recall does nothing. This reframes what would be worth testing next: not "does recall help on average" but "what predicts whether a given agent, on a given task, will act on a correct checkpoint versus spend its budget re-deriving what the checkpoint already told it" — a question about trust/verification behavior this six-arm design wasn't built to answer, since it only has two arms (A, D) implemented of the six in the original spec. Arm C (match-but-no-replay, i.e. inject the recall block without the replay-verdict metadata that tells the model how much to trust it) is the natural next arm to add: it would test directly whether *labeling* a checkpoint's confidence changes whether the model acts on it or re-verifies it.

**Tested that directly with `run-layer2-trust-pilot.ts`: a third arm, E, identical to D's recall block plus one sentence naming what `replayChecklist` actually computes ("the file(s) referenced above were re-checked against the current working tree immediately before this turn and are confirmed unchanged... you can act on this pointer directly without re-reading to confirm it first").** Content held fixed between D and E — only the trust label changes — on the same two tasks that produced the split above, instrumented with a new `repeatReads` counter (a `read_file` call on a path already read earlier in the same session, the exact behavior seen in `daaede29`'s D-arm trace). Flash (2 tasks × 3 arms × 10 trials = 60 sessions): on `daaede29`, telling the model the pointer was verified **doubled** repeat-reads instead of eliminating them (mean 1.10 for D → 2.20 for E) and cost more (median 36,696 → 45,377 tokens); on `6cbf927e`, E's success rate came in *lower* than D's (30% vs 50%, 3/10 vs 5/10) and cost more (median 24,662 → 29,548). Both directions are the opposite of the hypothesis. Pro (2 tasks × 3 arms × 5 trials = 30 sessions) split down the middle instead of confirming flash: on `daaede29`, E *did* reduce repeat-reads relative to D as hypothesized (mean 3.00 → 2.20) and cost less (median 73,925 → 66,549) — the one cell where the trust label worked as designed — but on `6cbf927e`, E again did worse than D (80% vs 100% success, repeat-reads mean 0.00 → 1.00, cost up). None of the D-vs-E success differences clear significance at these n (Fisher p ranges 0.65-1.0 across all four task×tier cells) — this is a small, targeted follow-up (96 sessions, ¥1.88), not a well-powered one.

**The honest reading: a bare assurance sentence is not a substitute for the real replay-verdict mechanism, and can backfire.** The one cell where it helped (`daaede29`/pro) is outnumbered by three cells where it didn't, including making the exact behavior it was meant to fix *worse* on the same task in the flash tier. A plausible reading is that an unsolicited "you can trust this, don't bother checking" is exactly the kind of claim a system prompt telling the model to verify before acting (this harness's own system prompt says "read the file you intend to change first") should make it *more* suspicious of, not less — asserting trustworthiness is not the same as demonstrating it, and a natural-language claim of freshness carries no more evidence than the content it's attached to. This suggests the real `replayChecklist` verdict — which is a computed, falsifiable claim (specific probes, specific fingerprints, an actual `k`-of-`n` prefix match) rather than an assertion — might behave differently from this stand-in, but that is now a distinct, still-open question this pilot doesn't answer: it tested whether *saying* "trust me" changes behavior, not whether showing the model *why* a checkpoint should be trusted does. A follow-up would need to render the actual verdict structure (probe results, confidence tier, scope ratio) rather than a single asserting sentence, closer to what `index.ts`'s real `recallForFirstTurn` would eventually format.

**Built that follow-up (`run-layer2-verdict-pilot.ts`) — and it makes the finding worse for confidence-labeling generally, not better.** This script runs the actual `replayChecklist` primitive from `src/replay.ts` against real git history for each task, using two real `git worktree` checkouts (the same technique `replay-decay-eval.ts` already uses): one `path-exists` probe on the source file, captured at the paired base commit and replayed against the working tree exactly as it stood at `task.parent`, the real moment a forked agent would have faced this checkpoint. For both tasks the real, computed verdict comes back identically: `partial` (k=1/1 — the file itself is unchanged since capture — but scopeRatio=0.00, meaning none of the *other* files that changed nearby since capture are ones this checkpoint's own trajectory touched). That is a genuine, calibrated, moderately-hedged signal, not a blank assurance — arm V renders it as plain numbers ("1/1 recorded checks still match... 0% of other nearby changes are accounted for... use this as one input, not a substitute for reading the file yourself") instead of E's confident sentence.

The result is not the finding "a fake assurance backfires but a real, honest verdict helps" — **both backfire, and the honest one backfires harder.** On `6cbf927e`, the task where plain recall (arm D) is unambiguously valuable, adding the real computed verdict cut its benefit roughly in half at every scale tested: flash D 70% success (7/10) vs V 50% (5/10); pro D 100% (5/5) vs V 20% (1/5) — collapsing all the way back to arm A's baseline (20%, 1/5) on the tier where D's effect is strongest. Pooling both tiers on this one task (n=15 per arm): D 80% (12/15) vs V 40% (6/15), Fisher p=0.06 — short of conventional significance but the closest any comparison in this whole investigation has come, on real oracle-verified outcomes. On `daaede29`, V shows the same cost/repeat-read increase over D that E showed (flash repeat-reads median 1.5→2, pro tokens median comparable to D's already-elevated cost) — no cell in either script, across four arm-pairs and two tiers, ever chose the labeled variant (E or V) over plain D on the task where recall's benefit was clearest.

**This reframes the mechanism.** It is not that models distrust false claims and accept true ones — a real, computed, appropriately-hedged verdict was *worse* than saying nothing at all about freshness. The more consistent pattern across both follow-ups: the plainer the recall block (content only, no commentary on how much to trust it), the more likely the model acts on it directly; any added text discussing the checkpoint's reliability — true, false, or genuinely calibrated — gives the model something to weigh, hedge against, or re-derive instead of just using, even when (as with V) the hedge is accurate. If this generalizes, it argues for keeping the freshness verdict *out* of the prompt entirely and using it only as a gate on *whether* to recall a checkpoint at all (which `graph.ts`'s node projection already needs to decide), not as text injected alongside the content for the model to read and reason about — the verdict computation stays valuable, but as a filter the harness applies before the model sees anything, not as a claim the model is asked to weigh itself. That is a materially different integration point than what the original six-arm design (C: content without verdict metadata vs D: content with it) assumed it was testing, and is now the more specific, better-motivated question for whatever wires this into `index.ts`'s real `recallForFirstTurn`.

**One more consequence of "gate, don't inject" needs stating plainly: a naive gate threshold would have thrown away the one clear win this whole investigation found.** The real computed verdict for `6cbf927e` — the task where recall is unambiguously valuable — is `partial`, not `fresh` (`verdictOf` in `src/replay.ts` downgrades any full probe pass with `scopeRatio < scopeThreshold` to `partial`, and this checkpoint's scope ratio is 0.00). A gate that only recalls on `fresh` would have suppressed recall entirely on the single task where it mattered most, in both model tiers. That is not a corner case: `replay-decay-eval.ts`'s own numbers (Verification, above) put `fresh` at roughly 50% one commit after capture and falling fast, meaning `partial` is not a rare edge state in an active monorepo — it is close to the modal outcome. A gate should therefore admit `fresh` and `partial` alike as plain content (no verdict text, per the finding above) and reserve suppression for `locational` and `dead`, where a probe result says the checkpoint's own anchor is actually gone, not just that unrelated nearby files moved.

**One honest check remained: `6cbf927e` and `daaede29` were picked *because* they split, so testing the verdict effect only on them risks reading a selection artifact as a general law.** Ran `run-layer2-verdict-pilot.ts` again against the other 6 of the original 8 mined tasks (flash, 5 trials each, 90 more sessions, no cherry-picking — whatever the task-selection script had already picked). The honest result tempers the earlier framing more than it overturns it: on 6 of these 8 tasks, essentially *nothing* happens in any arm — near-zero success for A, D, and V alike (`fecfabca`, `87f4e0b2`, `57fc6bc5`, `e58cc13d`, `0e390551` all 0/5 or worse across the board), meaning this task/budget combination is simply too hard for flash regardless of what's injected, and there's no room for a recall effect to show up one way or the other. One of the six (`600f3a31`) shows recall actively *hurting* relative to no recall at all, monotonically: A 60% (3/5) → D 20% (1/5) → V 0% (0/5) — a third real pattern (recall hurts, and the verdict commentary hurts further), distinct from both `6cbf927e` (recall helps, verdict erodes it) and `daaede29` (recall costs more for no benefit either way). Pooling all 8 tasks (150 flash sessions): A 6.0% (3/50), D 16.0% (8/50), V 10.0% (5/50) — D-over-A and V-under-D both hold directionally at the full-sample level, consistent with the two-task pilot, but neither clears significance at n=50/arm (Fisher p=0.20 and p=0.55). The two-task result was not a fluke in direction, but it was an unrepresentatively strong *magnitude* — most of the pooled effect is still carried by `6cbf927e` alone, and readers should weight the qualitative pattern (verdict commentary never beat plain content on any task where recall had a measurable effect to erode) more than the pooled percentages, which a single task still dominates.

Total cost for both follow-up pilots plus the 6-task generalization check (282 sessions): ¥4.77 (¥16.29 → ¥11.52), bringing the running total for the whole exploration/trust/verdict investigation to ¥13.09 across 525 real multi-turn agentic sessions.

**Checked against the actual production code, and the news is good: nothing here calls for a change today.** `renderRecall` in `src/index.ts` (the function `recallForFirstTurn` actually calls to build what a live session sees) injects exactly `{ nodeId, sourceSessionId, capturedThroughSeq, completedAt, score, actions, summary }` — content only, no freshness or confidence commentary of any kind. That is precisely the pilots' best-performing shape (arm D), not an oversight the pilots are arguing to fix. The finding is a warning against a specific, natural-seeming future change — wiring the `replayChecklist` verdict computed elsewhere in this note straight into this same JSON blob as an extra field for the model to read — rather than a call to alter what ships today. When that wiring happens, this note's evidence says: use the verdict to decide *whether* `renderRecall` returns a string at all (a `dead` or `locational` verdict suppressing recall the way a `score` below `minScore` already does), not as one more field inside the string it returns.

**Scoped the actual wiring work, and it's bigger than "call `replayChecklist` from `index.ts`" — `ContextGraphNode` has no `replayChecklist`/probe data at all yet, and the natural place to add it turns out to be the wrong place.** `graph.ts` is explicitly documented as pure extraction ("Pure extraction and ranking for the cross-session context graph", no I/O), and its existing tests (`graph.spec.ts`) construct fixtures and call `buildContextGraph`/`matchContextGraph` synchronously with no process boundary at all. Capturing a real replay checklist needs two facts that don't exist anywhere in the event log today: which paths a turn actually touched, and the git `HEAD` at the moment it completed. Neither can be derived after the fact inside `buildContextGraph` without breaking that purity — `computeScopeRatio` alone is a `git diff` subprocess call, and running one per historical node on every graph rebuild (the snapshot cache invalidates on every `session/event`) would make a currently-synchronous, mockable, pure function block on `execFileSync('git', ...)` per node. The correct capture point is therefore *once, at real turn-completion time* — wherever the agent loop already finalizes a `turn/end` event — not retroactively inside `context-graph`'s extraction. That is a `packages/core/session` event-schema change (session logs carry a `SESSION_FORMAT_VERSION`), not a `context-graph`-only change, and touching it properly means coordinating with whatever owns turn completion in `core/agent-loop`, not something to improvise inside this package alone.

The touched-paths half is more tractable than it first looked, though: this harness's own file tools use a small, stable, explicit set of argument shapes, confirmed by reading the actual tool definitions rather than guessing — `read`, `edit`, and `write` in `packages/fs/tool-fs` all take `file_path`; `str_replace_editor` in `packages/fs/tool-str-replace-editor` takes `path` instead. A `Record<string, string>` mapping tool name to its path-argument key, applied to `tool/call` event `arguments` (already logged verbatim per the session event schema), is precise and safe — no fuzzy JSON-key sniffing across an unaudited 200+-package tool ecosystem, and a tool not in the map simply contributes no probe, falling back to today's age-only freshness rather than guessing wrong. Note this reuses my own pilot scripts' `path` convention by coincidence, not by design — the real production tools mostly use `file_path`, which the pilot harness never had to know about since it drove a synthetic fixed tool set.

Given the schema-change dependency, this is not something to improvise unilaterally mid-loop: it needs its own scoped proposal (probably its own agent note) covering the `core/session` event addition, versioning/migration for existing logs without the new field, and only then the `context-graph` read-side wiring this note has been scoping. Recorded here so the next session picks up exactly where this one stopped, instead of re-deriving the same purity constraint from scratch.

### Does recall help more as one project accumulates history?

Every result above pairs one task with exactly its nearest prior same-file commit — a proxy for "one plausibly-related checkpoint exists," never for "this project has been actively developed for a while and has many checkpoints to draw on." That's a different, and arguably more realistic, claim: does an agent working in a project with real development history benefit from real candidate *selection* (the production `matchContextGraph` token-overlap ranking) against a *growing* pool, rather than a single hand-paired nearest commit?

**Built `run-layer2-accumulated-pilot.ts` to test this directly, reusing `graph.ts`'s actual `tokens()`/scoring logic (not an approximation of it) so the candidate selection is the real production behavior.** For each of the three packages with enough same-package mined tasks to simulate multiple development rounds (`packages/core/tools`: 6, `packages/core/session`: 5, `packages/code-runtime/code-runtime-python`: 4), tasks are ordered chronologically and replayed as rounds: round *N* runs arm A (no recall) and arm P (recall the single best token-overlap match, real `matchContextGraph` scoring, from a pool of all *N-1* earlier rounds' checkpoints — empty pool skips arm P on round 1). Pool size grows every round, exactly the "accumulated project history" scenario the question asks about.

Hit real, reproducible infrastructure flakiness first and had to fix it before any result could be trusted: `fetch` (Node's built-in, undici-based) failed nearly every call against this environment's local proxy — confirmed with a bare one-line `fetch()` outside the script, and confirmed that exponential-backoff retries of `fetch` itself still failed 7 consecutive attempts over two minutes on one occasion. Both `curl` and Node's older `node:https` module succeed against the identical URL every time. Switched `attemptCallModel` to `node:https`, and the flakiness disappeared entirely across the full run. Worth flagging for any future script in this investigation that still uses bare `fetch`.

**Result (3 packages × their rounds × 2 arms × 3 trials = 75 sessions, ¥0.58): no support for the accumulation hypothesis, on both axes tested.** Success: 1 of 75 sessions passed at all (`packages/core/session` round 4, arm A) — this task subset, selected purely for having enough same-package density to simulate rounds, turned out much harder than the earlier 8-task set (7.5%-10% success there vs. 1.3% here), so the success axis has essentially no statistical power to detect an accumulation effect either way. Cost is where there's an actual, clean, well-powered signal, and it points the wrong way: bucketing every arm-P session by the pool size it drew from, median cost *rises* as the pool grows — 31,915 tokens at pool size 1-2 (n=18) to 40,657 at pool size 3-4 (n=15). More accumulated history did not make the matched recall cheaper; if anything, more candidates to choose from produced a *more expensive* pick on average.

The likely mechanism is consistent with the strongest finding earlier in this note: recall only pays off when the matched checkpoint is actually the right one for the current task, and hurts when it's a plausible-looking distractor. A small pool (1-2 candidates from the same package) is more likely to contain only genuinely on-topic checkpoints; a larger pool (3-4) gives the token-overlap scorer more same-file-different-issue checkpoints to confuse for a real match — same file, overlapping vocabulary, wrong bug. Real accumulated project history does not straightforwardly help a token-overlap matcher; it gives it more opportunities to pick a distractor. This does not resolve the open question by itself (a richer scorer, or a larger same-project corpus with genuinely repeated patterns rather than one-off fixes to the same file, could behave differently), but as tested, "the same project has more history" was not itself a source of benefit — and lines up with the "gate, don't inject" and verdict-scoping findings above: a bigger pool without a way to tell a good match from a superficially-similar one just means more chances to pick wrong.

## Consequences

A checkpoint can now report a specific, falsifiable reason to trust or distrust it, instead of only its age. The load-bearing distinction and the scope-ratio guard are both intentionally coarse, conservative heuristics rather than a proof of correctness: `scopeRatio` in particular will downgrade some checkpoints that are actually still fine whenever unrelated files move without being listed as touched, trading recall for a lower false-`fresh` rate. Phase 2 (sandboxed exec-probe replay) and the L2 confidence tier remain open work, as does wiring this verdict into `graph.ts`'s node projection and the recall-injection path in `index.ts` — this note covers the probe/verdict primitive and its own test layer, not yet its integration into automatic recall.
