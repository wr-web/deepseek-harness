# Agent Note：为上下文图谱的 checkpoint 新鲜度加入重放校验

状态：proposed

[English](2026-09-05-context-graph-replay-verification.md) | 中文

## 问题

`@deepseek-ai/dsh-context-graph` 目前的新鲜度分类（`src/graph.ts` 中的 `fresh`/`aging`/`stale`）完全基于年龄：节点年龄小于其配置生命周期一半即为 `fresh`，与它描述的代码现在是否还是捕获时的样子无关。此前的设计笔记在"Consequences"一节里已经点出这个缺口："基于年龄的衰减能抑制旧上下文，但无法识别一次仓库修订；Git/文件指纹……仍是可扩展的方向。"一个看起来陈旧但其实仍然准确的节点会被无谓地丢弃，而一个看起来新鲜但代码早已重写的节点会被当作仍然成立而注入——后一种失败模式更危险，因为 agent 无法分辨一个"自信但错误"的 checkpoint 和一个真正正确的 checkpoint。

用完整重新推导（把整条轨迹重跑一遍）替代年龄判断并不可行：那会花掉这个功能本该节省的 token。可行的替代方案是：在不触发任何模型调用的前提下，检查 checkpoint 依赖的具体事实——它的轨迹实际读取过的文件、符号、命令输出——是否仍然成立。

## 决策

把一个 checkpoint 拆成三部分，各自的失效速度独立：身份与匹配字段（不变）、结构化结论加一个单独的死路字段，以及新增的**重放清单**——一份在捕获时记录下来的、有序的、无需模型调用的 probe 列表。每个 probe 记录 `{ seq, kind, path, capturedFingerprint, loadBearing }`。`loadBearing` 由一个廉价的写入时启发式判定（这个 probe 的输出是否喂给了后续某个工具参数、是否是某个随后被编辑文件的最后一次读取、是否出现在最终结论文本里）；只有承重 probe 计入新鲜度前缀，因此一次无关的漂移（多一行注释、一处无关代码的改动）不会让一个真正依赖仍然成立的节点被判失效。

重放按置信度分层执行，而不是做通用 diff：`path-exists` 和 `file-hash` 是精确层（L0）；`grep` 命中（符号是否仍出现在文件某处，行号位移不算失败）是结构层（L1）。两者都参与判定。给已清洗命令 stdout 用的层（L2）被有意延后——它需要先有噪声基线（见"验证"一节）才能安全参与判定。

判定本质是一个最长一致前缀计算：`k` 是按 `seq` 顺序、在遇到第一个不一致之前，有多少个承重 probe 重放一致；`n` 是承重 probe 总数。`k === n` 且捕获后改动的路径大部分被记录的触及路径覆盖（见下文 `scopeRatio`）→ `fresh`；一致前缀足够长 → `partial`；前缀很短但路径仍存在 → `locational`；每个 probe 都指纹为 `missing` → `dead`。`scopeRatio` 是对一个粗粒度盲区的补丁：代码库发生了大量改动，却恰好没有触碰 checkpoint 的 probe 读取过的任何地方——这种情况下满分重放不该被无条件信任，而应该降级。`computeScopeRatio` 用 `git diff --name-only <capturedHead>` 对比捕获时的提交与**真实工作树**（而非 `HEAD` 的干净检出），因为未提交的改动正是被 fork 出来的 agent 将要面对的真实状态。

这一版实现（`packages/context/context-graph/src/replay.ts`）只落地了上面这几种无沙箱 probe（`path-exists`、`file-hash`、`grep`），也就是设计规格里说的 Phase 1。Phase 2（对 exec probe 做写时复制沙箱重放，以 Phase 1 全过为前提）在这里尚未实现；仅含 Phase 1 probe 的 checkpoint 已经能产出一个真实判定，不依赖 Phase 2。

`replayChecklist` 从不抛出异常：重放基础设施本身失败——最具体的情形是捕获时的 commit 已经无法解析（历史被清理、被 rebase、或者检出是浅克隆）——会报告 `dead`，而不是把异常往外抛。这是刻意的设计，不是防御性编程的条件反射：这种环境漂移本身就是一个强新鲜度信号，而不是调用方需要单独兜底的错误状态。

`computeScopeRatio` 把 diff 限定在触及路径的所在目录，而不是整个 `cwd`。这不是最初的写法：`scripts/replay-decay-eval.ts` 用这个仓库自己的 `packages/core/session/src/types.ts` 的真实历史 checkpoint 去重放它自己后续的 commit，在没有目录限定（对整个仓库做 diff）的版本下，scope 守卫会把**每一个**样本都从 `fresh` 降级——哪怕只隔了捕获后的一个 commit——原因是在一个有 248 个项目的活跃 monorepo 里，仓库其他地方的无关活动永远会淹没一个以整棵树为分母的比值。改成按目录限定后，才得到了一条真正会衰减的曲线（一个 commit 之后还有 50% 保持 `fresh`，十个 commit 之后降到 14%）——这正是一个粗粒度保守守卫本该产出的样子。这类问题是 `tests/replay.spec.ts` 里的小型合成仓库天然发现不了的：它们按构造就是单目录仓库，所以这个 bug 在拿真实的多项目代码树去测之前一直是隐形的。

## 备选方案

**保留基于年龄的新鲜度，只加人工标记陈旧的机制。** 拒绝，因为这依赖有人主动发现漂移；设计目标是让检查在每个候选节点上免费自动运行。

**任何 probe 漂移都判失效。** 拒绝：一处无关注释或邻近行的重新格式化会杀死一个真实依赖完全未变的节点，这个代价比稍微宽松一点的判定更大。承重/附带的区分正是为了避免这一类假阳性。

**重放时对比 `HEAD` 而不是工作树。** 拒绝，因为 fork 继承的是用户真实的未提交状态，不是一次干净检出；对比 `HEAD` 相当于校验了一个 fork 出来的 agent 根本不会面对的世界。

**让所有 probe 类型（包括原始命令 stdout）都参与判定。** 拒绝，直到 scrubber 的噪声基线被测出来（见下文 Layer 0）；未经清洗的非确定性会让判定比它要替代的东西更嘈杂。

## 验证

`packages/context/context-graph/tests/replay.spec.ts` 覆盖了在任何模型调用或配对式线上实验之前就能跑的两层：噪声基线（对同一个未改动的 commit 重放二十次，以及从一个独立 clone 重放同一个 commit，两者都应得到完全相同的 `fresh` 判定），以及以真实 git 历史作为真值的验证器准确率（一个只改动了已记录路径的真实 commit 应保持 `fresh`；一次未被记录的路径改动应通过 scope 守卫把满分重放降为 `partial`；只发生在非承重 probe 上的漂移应被忽略；某个承重 probe 之后发生的真实内容变化应得到精确的 `k` 值和 `partial` 判定；前缀在路径仍存在的情况下立即中断应判 `locational`；路径被删除应判 `dead`）。全部测试跑在真实的临时 git 仓库上而非 mock 之上，因为验证器的前提本来就是观察真实工作树。

`scripts/replay-decay-eval.ts` 比合成测试走得更远：它从一个真实文件在多个真实历史 commit 上的导出符号自动推导 probe（用一个简单的正则启发式，权当"决策"一节里还没落地的写入侧捕获步骤的替身），然后通过真实的 `git worktree` 检出，把这些 probe 重放到这个仓库自己后续的历史上。对 `packages/core/session/src/types.ts`（152 个 commit，58 天的活跃历史）跑出来的结果是：8 个采样捕获点里，到第一次符号级别失效为止的中位时间是 27.8 天，其中两个在采样窗口结束时仍然成立——这是这个代码库第一个真实的半衰期估计，而不是基于年龄的方案里拍脑袋的 30 天常数。上面提到的 `computeScopeRatio` 目录限定 bug，正是这个脚本发现的。

`scripts/build-layer2-taskset.ts` 用同样的思路构建 Layer 2 的任务那一侧：来自这个仓库自己历史的真实 commit，不是合成的也不是借来的。对每一个在同一个 package 里把源码改动和测试改动绑在一起的 commit，它不相信 commit message——而是把工作树临时改写成"父提交的源码 + 新 commit 的测试"，期待测试失败（RED，修复还没落地）；再改写成"新 commit 的源码"，期待测试通过（GREEN）；不管结果如何，每次都会立刻把所有改动过的文件恢复原样。它还会检查 PASS_TO_PASS（SWE-bench 的说法）：GREEN 之后，整个包的测试目录（不只是目标 spec 文件）也必须全过——一个悄悄弄坏了别的地方的"修复"不值得留作任务。扫描 216 个包找到 887 个结构上合格的 commit。先对 150 个候选做的第一次采样接受了 15 个；把候选面放宽到 400 个之后，接受数涨到 38 个，覆盖了多得多的包。400 个里有 326 个被拒绝是因为 commit 自己的改动单独放进去还是到不了 GREEN（通常说明真正的修复还牵动了这个工具只看单一 package 之外的某个文件，是诚实的范围局限而不是 bug），21 个是因为父提交的代码本身就已经满足新测试，还有 15 个是被 PASS_TO_PASS 检查揪出了窄范围检查本身发现不了的回归。两个脚本都会把工作树恰好还原成运行前的样子；`build-layer2-taskset.ts` 在工作树对已跟踪文件有未提交改动时会直接拒绝运行。

`scripts/build-context-pairs.ts` 在此基础上补上了六臂实验真正需要的结构：SWE-ContextBench（arXiv:2602.08316）指出现有 benchmark 都把每个任务当独立的，不测 agent 能不能复用之前相关任务的经验，为此专门构造了一份 base+related 的任务配对数据集。这个脚本对着 `layer2-taskset.json` 做同样的事——对每个已验证任务，往回找（刻意只找**最近的一次**先前触碰，不是窗口内所有 commit：早期草稿是"窗口内两两配对"，结果被频繁改动的文件的组合爆炸产出了 133,075 对，作为任务集完全不可用）触碰过同一个源文件的最近一次先前 commit，窗口设为 30 天——这个数字对应 `replay-decay-eval.ts` 测出的约 27.8 天半衰期。38 个已验证任务全部找到了符合条件的先前 commit；大多数是当天（也就是紧邻的、后来这次修复所纠正的那次 feature/refactor commit本身），少数是 5-10 天之前。这正是 A/B/D 臂需要的原始材料：一个 base checkpoint，加上一个召回系统理论上能帮上忙的后续任务。

尚未开始：完整设计规格里的线上影子模式闭环，以六臂实验本身先能给出有信息量的结果为前提。相对于它借鉴的这些成熟开源工具，现在还缺：去污染检查（GitBug-Java 的做法——只挖模型训练截止日期之后的 commit——对一个公开模型从没见过的私有 monorepo 不完全适用，但如果未来在这份自家历史上做微调，这一条就会变得需要）、难度分级，以及（见下文）一种能测"项目积累的历史越多、召回是否越有用"这个具体假设的方法，而不只是"离得最近的那一个先前 commit 有没有用"。

**A/D 试跑，n=1×3（`scripts/run-layer2-pilot.ts`），用真实模型（`deepseek-v4-flash`）：** 花了四次尝试才拿到一个能信的结果，这个排查过程本身就值得记下来。第一次（4000 token 上限）6 次调用里 4 次被截断。把上限调到 8000、再调到 32000 都没用——32000 上限时仍有两个任务撞到 `finish_reason: "length"`，而且**可见的 `content` 字段完全是空的**：32000 个补全 token 全部花在了这个模型默认开启的"思考模式"上，它的思维链会算作补全 token 计费，但会单独放在 `reasoning_content` 字段里返回，这次脚本压根没读这个字段（见 DeepSeek 的[思考模式文档](https://api-docs.deepseek.com/guides/thinking_mode/)）。上限调得再高也只是给看不见的推理更多空间跑，永远不会更快抵达真正的答案。传入 `thinking: { type: "disabled" }` 直接解决了问题——第四次尝试 6 次调用全部 `finish_reason: "stop"`，输出量也回到了合理的 1.5k-3.8k token。

截断问题真正解决之后，看到的实情是：三个任务里有两个失败是有正当理由的——模型返回了完整、格式良好的文件，只是没把 bug 真正修对（直接检查过：返回的代码语法完整，不是被切断的），这是一个快/便宜模型在这类稍微细节一点的修复上真实存在的能力局限，不是脚手架的缺陷。第三个任务（`760bc9aa`，`util/timeout`）两个臂都通过了，但它的 D 臂对 A 臂的 token 差值**在前三种不同配置下每次都不一样**——一次净省，一次净费，第三次是小幅净费——而且 `temperature` 都设的是 0，输入完全相同。当时看起来这就是设计规格自己给出的 Layer 2 统计警告（"agent 方差很大，n=1 的对比是噪声"）的现场演示。

**其实不完全是——这个修正很重要。** 把同样三个任务在**固定不变**的配置下（关闭思考模式、max_tokens 16000）各跑 `TRIALS=10` 次，而不是像之前那样每次单发尝试都换一套配置：结果回来几乎是确定性的。两个任务在两个臂上 10 次全部输出了完全相同的 token 数（`87f4e0b2`：每次都是 5587/6126；`8f5c592b`：12135-12162/12677-12781，波动不到 1%）；第三个（`760bc9aa`）波动也只有约 5%（A 臂 5821-6120，D 臂 6340-6362）。之前那个"每次符号都不一样"，根本不是模型本身的随机性——而是在比较**不同** token 上限和不同思考模式设置下跑出来的结果，这压根算不上一次受控对比。真正控制住变量之后，答案就不再摇摆了。

而这个受控之后的答案清晰、一致，但对"能省 token"这个假设不利：**D 臂在三个任务上、每一次试验都比 A 臂贵**——中位数差值分别是 −539、−507、−598（负数=D 更贵），原因是召回块本身就要多花约 500-600 个输入 token，而且没有在输出长度上省回来。D 真正帮上忙的是另一个完全不同的维度：`760bc9aa` 的成功率在注入召回后从 90%（9/10）提升到 100%（10/10）——一个真实的、虽然样本很小的可靠性信号，跟成本问题正交、无关，这正是六臂设计想要避免的"用一个数字掩盖两件不同事情"的情况。60 次调用总花费：¥0.57（跑前跑后各查了一次 `/user/balance` 确认）。脚手架本身在第一次尝试时也确实有一个真 bug（写成了 `return run()` 而不是 `return await run()`，导致本该包住整个异步模型调用和文件改写的恢复 `finally` 块提前触发，留下六个文件处于脏状态；已修复，之后每次跑——包括这一次——都验证工作树恢复干净）。

这三个任务的结论都不能推广到"这一个 flash 级模型、这三个小的单文件任务、这一种召回块格式"之外。但它确立了一件事：这套脚手架是端到端可信的（真实 oracle、不再截断、恢复验证过、花费查证过），而在任何更大规模的重跑里最重要的一条经验是：**被比较的所有试验必须固定同一套模型配置**——前三次尝试里看起来像"噪声"的东西，其实是实验设计本身的噪声，不是设计规格警告的那种"agent 方差"，把两者混为一谈会得出错误的结论。

**扩大到 34 个任务 × 2 个臂 × 5 次试验（340 次调用），验证了同一个方向，还多出一个更有意思的负面结论。** `run-layer2-pilot.ts` 不再写死 3 个 commit——它现在会跑所有有配对的、单源文件单测试文件的任务（38 个里的 34 个），动机正是你提出的假设：同一个项目反复开发下去，召回是不是会随着代码库积累的历史越来越有用，而 3 个任务的样本根本没法回答这个问题。结果是：**34 个任务里没有一个例外**，D 臂在每一次试验里都比 A 臂贵——中位数差值从 −200 到 −695 不等，整体中位数 −537.5。按配对的先前 commit 有多"新"分桶（`<1 天`：26 个任务，中位数 −540；`1-7 天`：5 个任务，中位数 −437；`≥7 天`：3 个任务，中位数 −336）显示成本随着先前 commit 变老而略微收窄，但更稀疏的那几个桶只有 3-5 个任务，这个趋势不值得当真——之所以写出来，是因为它跟"越新、越相关的上下文帮助越大"这个直觉正好相反，而不是因为它统计上站得住。

成功率这次走向了跟 3 任务试跑相反的方向：整体上 A 臂试验成功率 35.9%，D 臂 31.8%——平均下来召回让结果略微变差，而不是变好，这是在任务数足够多、不会被一个"走运"的任务带偏之后测出来的。大多数任务两个臂的成功/失败结果没变；少数几个任务在两个方向上都发生了翻转（`698fdaea` 加了召回后 100%→0%，`acc628f3` 40%→0%，`600f3a31` 100%→80%；`ca119b0e` 则是 80%→100%）。340 次调用总花费：¥7.63（余额从 ¥13.84 降到 ¥6.21）——比之前那次 60 次调用、每次 ¥0.0095 的均价高出不少，因为放宽候选面之后混进了几个大得多的文件（818 行的 `py-types.ts`、656 行的 `protocol.ts`），它们的整文件重写 prompt 单次就要 15,000-48,000 token，不是那些约 250 行文件的 5,000-12,000。

**这次跑清楚了什么，又没解决什么。** 对于具体测的这件事——把时间上最近的那一次同文件先前 commit，格式化成截断的原始 diff，注入给一个 flash 级模型去重写整个文件——现在有了一个样本量足够、跨 34 个真实多样任务的负面结论：不省 token，也没有可靠地提高正确率。但它**没有**测到促成这次扩大规模的那个假设："同一个项目反复开发多轮之后，召回是不是更有用"，这是一个关于**积累的历史**（有很多候选 checkpoint 可挑，且是按相关性挑出来的）的主张，而这套设计测不了它，因为它每次都只注入唯一一个候选（时间上最近的那个），从来不是真实 `matchContextGraph` 那种词法排序会从更丰富的候选池里挑出来的东西。它**也**根本没测到这套设计真正的价值主张：上面每一个任务都是直接把失败的测试和确切的源文件喂给模型。答案的位置已经在 prompt 里写明了，这种情况下根本没有"探索"这回事可以省——多塞一段召回文本当然只会加成本。

**`run-layer2-exploration-pilot.ts` 测的才是真正的主张：召回能不能省探索成本。** 一个真正的多轮工具调用 agent（`list_directory`、`read_file`、`search_code`、`submit_fix`）被扔进任务所在的 package，只给一句 commit message 级别的描述——绝不给文件路径或测试内容——必须自己找到 bug 在哪，就像一个真实的全新会话真的要做的那样。D 臂在 agent 第一轮之前，会插入和之前试跑一样的"Reused context checkpoint"块，跟 `index.ts` 里真实的 `recallForFirstTurn`做的事完全一样。无论 agent 的 `submit_fix` 最终碰的是哪个文件，这个 package 里所有被 git 跟踪的文件都会先快照、跑完后原样恢复——因为它完全可能探索到错误的文件上去。

正式开跑之前，两次冒烟测试暴露了两个 bug，都修了并重新验证过：`resolveWithinPackage` 会拒绝空的相对路径，而这恰好就是请求 package 根目录（`.`）解析出来的结果——agent 第一次调用 `list_directory('.')` 每次都在悄悄失败，后面自然什么都找不到。还有一次，一个"refactor"任务（跨包的 Remote 接线管道代码）把 agent 引去 `node_modules` 里翻找一个符号定义，白白烧掉约 10 万 token 也没收敛——修法是把 `node_modules` 排除在三个读取类工具之外，并把任务选择范围限定在 `fix(...)` 这种小修复类型的 commit 上，它们比 refactor 更可能就窝在一个能找到的地方。

**正式跑（8 个任务 × 2 个臂 × 3 次试验 = 48 个会话）跑出来的，比一个成本数字更根本。** 成功率：**两个臂、全部 48 个会话，0%。** 这个 flash 级模型基本上完全做不了"真实探索再修复"这件事——哪怕少数几次真的调用了 `submit_fix`，产出的修复照样过不了 oracle。这让假设里"成功率"那一半根本没法测：两个臂都从来没成功过，压根没有信号可比。成本那一半还是能测的，而且测出来的结果毫不含糊：**8 个任务里没有一个例外**，D 臂用的 token **和**轮数都比 A 臂多（整体中位数轮数 5 对 7，token −11,553）——召回没有缩短探索，反而拉长了探索，跟假设正好相反，而且完全没有成功率上的好处能抵消这个成本。

**换一个更强的模型（`deepseek-v4-pro`）想给"成功率"这个问题一次公平的机会，结果先测出来的是一个真的工具 bug，不是答案。** 一次 2 任务的冒烟测试显示模型探索得很像样（真的定位到了正确的文件），但工具调用配额用完的时候还没走到 `submit_fix` 这一步——把上限提到 20 次工具调用/18 轮之后，跑完整的 8×2×2 设计（32 个会话）时，日志里冒出一堆 `git grep` 的致命错误（"Unmatched ( or \("）：模型自己发出的搜索请求里，很大一部分——像 `it(`、`describe(`、`isJsonValue(value[i]` 这种再正常不过的代码片段——都不是合法的扩展正则表达式。`search_code` 在悄悄地把一个坏掉的工具喂给模型，覆盖了相当大比例的正常搜索请求，这根本不是在公平地测它的探索能力。修法是在正则解析失败时回退成固定字符串搜索（`-F`）。

**用同样的 8×2×2 设计、修完 bug 后重跑一遍，成功率毫无变化，也证实了之前那个 bug 并不是真正的瓶颈：两个臂、两次 pro 模型跑（总共 64 个会话），依然是 0%。** 哪怕换了一个明显更强的模型、给了充裕的探索预算、搜索工具也修好了，光凭一句 commit message 级别的描述，也没法在这个仓库里可靠地探索出一个正确的修复。这本身就是个值得记下来的结论：这种任务设定（冷启动的多包代码库、极简的 prompt、有限的工具面）难到光靠换模型档位——试了两次——都过不去。

不过成本这条线，强模型跑出来的结果跟 flash 明显不一样，而且两次 pro 模型的跑法都一致：flash 是**每一个**任务 D 臂都更贵，没有例外；pro 却是 8 个任务里有 5 个 D 臂更便宜，两次跑都是这样（整体中位数省下的 token：搜索工具有 bug 那次是 +14,011，修完之后是 +20,930），虽然具体是哪 5 个任务在两次跑之间有些变动。这个结果要谨慎看待——每个臂只有 2 次试验，而且这些会话最后全都是失败的，所以严格说这是"一次失败尝试的成本"，不是"一次成功修复的成本"——但这个方向在两次跑里都复现了，跟 flash 的结论不一样，是一个真实的差异。一个说得通的解释是：更强的模型哪怕最终没能给出正确答案，也能部分利用注入的上下文缩短本来要做的探索。这跟"召回从来没用"是完全不同的、更有意思的结论，而且如果直接把 flash 的结果外推到更强模型身上，预测出来的方向正好是反的。

整个探索成本调查总共花费：¥0.47（flash，48 个会话）+ ¥2.78（pro，32 个会话，搜索有 bug）+ ¥2.36（pro，32 个会话，搜索已修复）= **¥5.61**，跑了 112 个真实的多轮 agentic 会话（余额 ¥26.09 → ¥20.15）。现在真正卡住继续往下测的，不是预算，而是模型能力和任务设定本身：下一步该做的，是换一个强模型确实能偶尔**成功**的任务集（或者仓库），这样假设里"成功率"那一半才有机会显出信号，而不是只能测成本那一半。

**纠正：上面所有"0%"的结果都不成立——坏的是 oracle 本身，不是模型。** `run-layer2-exploration-pilot.ts` 里的 `runVitestResult`/`runVitestExitCode` 是相对 `packageDir` 去跑 vitest 的。但这是一个 216 个包的 pnpm workspace，单个包自己并没有 `node_modules/vitest`——只有 monorepo 根目录的 `node_modules` 才有。上面总结的全部 144 个会话（48 个 flash + 64 个 pro）里，每一次 `submit_fix` 调用触发的 oracle 检查，走的都是一条永远解析不到模块的路径，而这种失败是"默认失败"的：不管模型给出的修复实际上对不对，它都会报 FAIL。也就是说，"两个臂都是 0%"这个结论、flash 的成本对比、pro 的成本对比，测的其实都是"一个成功与否根本无法被观测到的会话的成本"，而不是"针对真实 oracle 的真实尝试的成本"。这个 bug 不是靠某次测试跑挂发现的，而是靠行为证据：某段会话记录里，模型在调用 `submit_fix` 之后紧接着去查看 `package.json` 和 `node_modules`，这正是模型在应对依赖解析错误时的反应模式，而不是应对语义层面测试失败的反应——这恰好就是一条模块解析路径坏掉之后，从模型视角看起来的样子。修法是把 `repoRoot` 一路传进 `runSession()`，改成用仓库相对路径、从 workspace 根目录调用 `runVitestResult(repoRoot, task.testFiles)`——`run-layer2-pilot.ts` 里本来就用对了的同一套模式。修完之后立刻跑了一次 3 任务 / 1 次试验的 flash 冒烟测试，直接跑出一个真实的 PASS（`6cbf927e`，5 轮，1 次 `submit_fix`，19,562 token）——这是整个探索成本调查里第一次真实的成功，既证实了这个 bug 是真的，也证实了修复是有效的。

**用修好的 oracle 重跑 flash 的完整 8×2×5 设计（80 个会话）：成功率现在是真的了，但很小，两个臂之间在统计上区分不开；整体成本仍然是不召回更划算，但这个汇总数字掩盖了两个方向相反的任务级效应。** A 臂：7.5% 成功（3/40），token 中位数 27,819，轮数中位数 8。D 臂：10.0% 成功（4/40），token 中位数 39,161，轮数中位数 8。对 3 比 4 的成功次数做双侧 Fisher 精确检验，p=1.0——在这个样本量下没有方向性信号。把每个 A 臂会话和同一任务、同一试验序号的 D 臂会话配对，取 token 差值（n=40 对）：中位数 −4,833（负数表示 D 更贵），40 对里只有 9 对是 D 更便宜。多出来的成本集中在缓存输入 token 上（D 的中位数 31,360，A 是 24,320）——也就是召回块本身，而不是输出变长——这跟单次生成 pilot 之前的发现一致：注入的这一块是一笔固定成本,模型并不总能靠它省回来。更有意思的是任务级别的拆分：在 `6cbf927e` 这个任务上，D 臂 5 次里成功 3 次，A 臂 5 次里 0 次成功——召回在这里是决定性的。而在 `600f3a31` 上正好相反：A 臂 5 次里成功 3 次，D 臂只成功 1 次——召回在这里是明显帮倒忙的。这两个效应在汇总出来的 7.5% 对 10.0% 这个数字里基本抵消了，而这正是设计规格里强调多臂框架要防住的失效模式：只看一个汇总统计量,会报告"没有效应",却把两个真实的、方向相反的、任务特定的效应都藏在了底下。

**用修好的 oracle 重跑 pro 档位（8 个任务 × 2 臂 × 3 次试验 = 48 个会话，轮数/工具调用预算跟 flash 对齐,保证公平对比）：召回效应比 flash 更大,方向更明显,但在这个样本量下还是没到统计显著。** A 臂：4.2% 成功（1/24），token 中位数 44,649，轮数中位数 10。D 臂：12.5% 成功（3/24），token 中位数 46,401，轮数中位数 9——成功率是 3 倍，但对 1 比 3 这两个成功次数做双侧 Fisher 精确检验，p=0.61（事件太少，分不出跟噪声的区别）。整体 token 成本基本打平（配对中位数 +1,511 个 token，偏向 D 更便宜；但均值是 −3,070，偏向 A 更便宜——中位数和均值方向不一致,本身就说明这是被几个离群值拉偏的分布,而不是一个干净的效应；24 对里 D 更便宜的有 13 对，A 更便宜的有 11 对）。把两个模型档位的数据汇总起来（flash 40 + pro 24 = 每个臂 64 个会话）：A 6.25%（4/64），D 10.9%（7/64），汇总后 Fisher p=0.53——两个档位各自看、汇总起来看，方向都一致地在 1.7 到 3 倍之间，但在这个样本量下都还没到显著。

**同一个任务 `6cbf927e` 在两个模型档位上复现了完全一样的决定性效应——这是整个调查里最强的单项发现。** flash：D 臂 5 次里成功 3 次，A 臂 5 次里 0 次。pro：D 臂 3 次里成功 3 次，A 臂 3 次里 0 次。两个模型合起来看，D 臂一共 6 次试验成功、0 次失败；A 臂一共 8 次试验、0 次成功。看工具调用记录就能解释原因：召回块直接点名了真正的文件（`src/startup.ts`）和相关的测试，于是 D 臂的 agent 走的路径是 `list_directory` → 一次精准的 `search_code` → 直接 `read_file` 读对的两个文件 → `submit_fix`，5-7 轮就收敛了。A 臂的 agent 没有这个线索，把预算花在检查一个看起来合理但其实错的目录（`lib`）、把 `src/index.ts` 重复读了两遍、搜索一些根本不在正确文件里出现的词——而且每一次追踪到的案例,都是在轮数预算耗尽之前从没调用过 `submit_fix`。这正是探索成本这个假设本该起作用的样子：一个能点名正确文件的 checkpoint，能把一次耗尽预算的搜索变成一段五轮的对话。

**任务 `daaede29` 在两个档位上复现了完全相反的模式,同样很能说明问题。** flash：D 比 A 的 token 中位数多花 14,731。pro：D 多花 41,720。两个模型的两个臂在这个任务上都从来没成功过。这里的召回块同样正确地点名了对的文件（`turn-error.ts`）和测试——D 臂的 agent 确实也立刻定位到了它，跟 `6cbf927e` 一样——但接下来卡住了：pro 档位的记录显示，它把测试文件里*同一段* 120 行的区间重复读了两遍，接着又做了三次独立的 grep 想精确定位某一条断言，把整个工具调用预算都花在反复核实一个已经找到的文件上，而不是收敛到一个修复方案。A 臂是盲搜，花的预算差不多，但花在了真正不同的探索上（一直没找到那个文件，但也没有陷入反复读同一个文件的循环）。这里的教训是：正确缩小"该看哪里"的范围，不代表 agent 就一定能更快收敛——一个 checkpoint 可以点对文件，模型却仍然可能把整个预算都花在对着同一个文件反复自我怀疑上，而不是直接照着做。只有当模型真正信任并且照着给到的信息去行动时，召回才会缩短探索；如果它不信任，多出来的上下文就是纯粹的开销，没有任何补偿性收益。

**修好 oracle 之后重跑的总花费：131 个会话花了 ¥2.71（¥19.00 → ¥16.29）：3 个 flash 冒烟测试会话 + 80 个 flash 会话（¥0.85）+ 48 个 pro 会话（¥1.86）。** 加上修复之前那些（现在已经作废的）跑法花掉的 ¥5.61，整个探索成本调查到目前为止一共跑了 243 个真实的多轮 agentic 会话，花费 ¥8.32。

**这把这个假设放在了什么位置。** "召回能省探索成本"这件事，在两个模型档位的汇总数据上都不成立——汇总的 token 和成功率数字，在两个臂之间统计上区分不开，而且样本量小到无法排除一个真实但温和的效应朝任一方向存在。但这不代表这个假设就是单纯错的：在一个 checkpoint 正确点名了文件*并且*模型确实照着行动的任务上（`6cbf927e`，在两个模型档位上复现,六次全对零次全错），这个效应是真实的、很大的、一致的；在一个 checkpoint 同样正确点名了文件、但模型不够信任、非要重新核实一遍的任务上（`daaede29`，同样复现），这个效应也是真实的、很大的，但方向是*负*的。汇总出来的接近于零的效应，是这两个真实的、方向相反的、依赖具体任务的效应取平均的结果，不是"召回什么都没做"的证据。这也重新定义了接下来值得测试的问题：不是"召回平均来说有没有用"，而是"什么因素能预测一个给定的 agent，面对一个给定的任务，会不会照着一个正确的 checkpoint去行动，还是会把预算花在重新推导 checkpoint 已经告诉它的东西上"——这是一个关于信任/核实行为的问题，而现在这套六臂设计还回答不了，因为原始规格里的六个臂目前只实现了两个（A、D）。C 臂（匹配但不重放，也就是只注入召回块本身、不附带告诉模型该信任到什么程度的 replay-verdict 元数据）是接下来最自然要补的一个臂：它能直接测出，给 checkpoint 的可信度打上标签，会不会改变模型是照着行动还是重新核实。

**用 `run-layer2-trust-pilot.ts` 直接测了这个问题：加了第三个臂 E,内容跟 D 的召回块完全一样,只多了一句话,点出 `replayChecklist` 实际算出来的东西**（"上面提到的文件，在这一轮开始之前已经针对当前工作区重新核实过，确认自捕获以来没有变化……你可以直接照着这个线索行动，不需要再重新读一遍来确认它"）。D 和 E 之间内容完全固定，只有信任标签这一个变量——用的是产生上面这个分化结果的同一组两个任务，另外加了一个新的 `repeatReads` 计数器（同一个会话里对已经读过的路径再调用一次 `read_file`，正是 `daaede29` 的 D 臂记录里看到的那种行为）。flash（2 个任务 × 3 个臂 × 10 次试验 = 60 个会话）：在 `daaede29` 上，告诉模型这个指针已经验证过，重复读取次数不但没有消失，反而**翻倍**了（D 的均值 1.10 → E 的均值 2.20），花费也更多（token 中位数 36,696 → 45,377）；在 `6cbf927e` 上，E 的成功率反而比 D **更低**（30% 对 50%，3/10 对 5/10），花费也更高（token 中位数 24,662 → 29,548）。两个方向都跟假设相反。pro（2 个任务 × 3 个臂 × 5 次试验 = 30 个会话）没有印证 flash 的结论,而是各打五十大板：在 `daaede29` 上，E 确实按假设预期的方向减少了重复读取（均值 3.00 → 2.20），花费也更低（token 中位数 73,925 → 66,549）——这是唯一一个信任标签按设计起作用的格子——但在 `6cbf927e` 上，E 又一次表现得比 D 差（成功率 80% 对 100%，重复读取均值 0.00 → 1.00，花费上升）。这四个"任务×档位"组合里，D 和 E 的成功率差异没有一个能过显著性检验（Fisher p 在 0.65 到 1.0 之间）——这是一次小规模的针对性跟进实验（96 个会话，¥1.88），不是一次统计功效充分的实验。

**老实说：一句干巴巴的保证话术,替代不了真正的 replay-verdict 机制，甚至可能起反作用。** 唯一一个信任标签起了作用的格子（`daaede29`/pro），被另外三个没起作用的格子盖过了，其中还包括在 flash 档位上,在同一个任务上把它本来要修的那个行为变得*更糟*。一个说得通的解释是：一句没人要求、主动声明"你可以相信这个，不用检查"的话，恰恰是这套 harness 自己的系统提示词（"先读一遍你打算改的文件"）教模型在行动前要核实的那种说法——应该让模型*更*怀疑，而不是更不怀疑；宣称"这值得信任"跟证明"这值得信任"不是一回事，一句关于新鲜度的自然语言断言，本身并不比它所依附的内容多提供任何证据。这也说明真正的 `replayChecklist` verdict——一个计算出来的、可证伪的结论（具体的探针、具体的指纹、一个真实的 `k` 比 `n` 前缀匹配），而不是一句断言——可能会跟这个替代品表现不一样，但这已经是一个独立的、还没回答的新问题了：这次测的是"说一句'相信我'会不会改变行为"，而不是"给模型展示*为什么*该信任这个 checkpoint 会不会改变行为"。后续要跟进的话，需要把实际的 verdict 结构（探针结果、置信度档位、scope ratio）渲染出来，而不是塞一句断言式的话——更接近 `index.ts` 里真正的 `recallForFirstTurn` 将来会输出的样子。

**把这个后续跟进做出来了（`run-layer2-verdict-pilot.ts`）——结果让"打标签会拖后腿"这个结论变得更严重，而不是更轻。** 这个脚本针对每个任务，用两次真实的 `git worktree` checkout（跟 `replay-decay-eval.ts` 已经在用的技术一样），对 `src/replay.ts` 里真正的 `replayChecklist` 原语跑真实的 git 历史：在配对的 base commit 上给源文件设一个 `path-exists` 探针作为捕获时的记录，然后针对 `task.parent` 那个时间点的工作区状态重放——这正是一个被 fork 出来的 agent 真正会碰到这个 checkpoint 的那个时刻。两个任务算出来的真实 verdict 完全一样：`partial`（k=1/1——文件本身自捕获以来没变——但 scopeRatio=0.00，意味着捕获之后附近变化的*其他*文件里，没有一个是这个 checkpoint 自己的轨迹碰过的）。这是一个真实的、经过校准的、语气偏保守的信号，不是空口保证——V 臂把它渲染成大白话的数字（"1/1 项记录的检查仍然匹配……捕获之后附近的其他变化里有 0% 是这个 checkpoint 自身轨迹能覆盖到的……把这个当作参考之一，不要替代你自己去读文件"），而不是 E 那种自信满满的断言句。

结果不是"假的保证话术会拖后腿，但真实、诚实的 verdict 会有帮助"——**两者都拖后腿，而且诚实的那个拖得更狠。** 在 `6cbf927e` 这个纯召回（D 臂）明显有用的任务上，加上真实计算出来的 verdict，在测过的每一个规模上都把 D 的收益砍掉了大约一半：flash 上 D 成功率 70%（7/10）对 V 50%（5/10）；pro 上 D 100%（5/5）对 V 20%（1/5）——在 D 效应最强的那个档位上，V 直接被打回了 A 臂的基线水平（20%，1/5）。把两个档位在这一个任务上汇总（每个臂 n=15）：D 80%（12/15）对 V 40%（6/15），Fisher p=0.06——还没到常规意义上的显著，但这是整个调查里，在真实 oracle 验证的结果上,最接近显著的一次比较。在 `daaede29` 上，V 表现出了跟 E 一样的成本/重复读取上升（flash 重复读取中位数从 1.5 到 2；pro 的 token 中位数也跟 D 本来就偏高的花费差不多）——两个脚本、四组"臂对比"、两个模型档位，没有一次是打了标签的版本（E 或 V）在召回收益最明显的任务上赢过纯净版的 D。

**这重新定义了背后的机制。** 不是说模型会不信假的断言、会信真的断言——一个真实的、计算出来的、恰如其分打了折扣的 verdict，表现居然*比什么都不说*还差。两次跟进实验加在一起，更一致的规律是：召回块越"干净"（只有内容，不附带任何关于该信任到什么程度的评论），模型越有可能直接照着行动；任何讨论 checkpoint 可靠性的附加文字——不管是假的、真的，还是像 V 这样真正经过校准的——都会给模型一个东西去权衡、去打折扣、或者干脆重新推导一遍，而不是直接拿来用，哪怕（就像 V 这样）这个折扣本身是准的。如果这个结论能推广开来，那就说明应该把新鲜度 verdict 完全挡在 prompt 之外，只用它来当"要不要召回这个 checkpoint"的门槛（这正是 `graph.ts` 的节点投影本来就需要做的判断），而不是当成注入到内容旁边、让模型自己去读、自己去权衡的一段文字——verdict 的计算本身仍然有价值，但它应该是 harness 在模型看到任何东西*之前*就应用的一道过滤器，而不是丢给模型自己去掂量的一个论断。这跟原始六臂设计（C：内容不带 verdict 元数据，对比 D：内容带 verdict 元数据）当初以为自己在测的东西，是一个实质上不同的集成方式，也是接下来把这套东西接进 `index.ts` 真正的 `recallForFirstTurn` 时，更具体、更站得住脚的问题。

**"只当门槛、不注入文字"还有一个后果需要说清楚：一个天真的门槛设定，会把这整个调查里唯一一个明确的胜利给扔掉。** `6cbf927e`——那个召回明显有价值的任务——算出来的真实 verdict 是 `partial`，不是 `fresh`（`src/replay.ts` 里的 `verdictOf` 会把任何 `scopeRatio` 低于 `scopeThreshold` 的满分探针结果降级成 `partial`，而这个 checkpoint 的 scope ratio 正好是 0.00）。一个只在 `fresh` 时才召回的门槛，会在两个模型档位上都把召回明明最有用的这一个任务的召回完全压掉。这不是什么边角情形：`replay-decay-eval.ts` 自己算出来的数字（见上面"验证"部分）显示，捕获之后过了一个 commit，`fresh` 的比例大概只剩 50%，而且还在快速下降——也就是说在一个活跃的 monorepo 里，`partial` 不是小概率的边缘状态，反而接近众数。所以门槛应该把 `fresh` 和 `partial` 一视同仁地放行（都只放内容,不带 verdict 文字，按上面的发现来），只把 `locational` 和 `dead` 留给真正要压制召回的情形——那才是探针结果说 checkpoint 自己的锚点确实没了,而不仅仅是附近有些不相关的文件动了。

**还剩一个诚实的检查要做：`6cbf927e` 和 `daaede29` 之所以被选中，正是因为它们的结果分化了，所以只在这两个任务上测 verdict 效应，有把选择偏差当成普遍规律来读的风险。** 又针对最初挖出来的 8 个任务里剩下的 6 个，重新跑了一遍 `run-layer2-verdict-pilot.ts`（flash，每个任务 5 次试验，多跑了 90 个会话，没有挑任务——任务选择脚本本来选出来是哪几个就是哪几个）。老老实实看结果，这次更多是把之前的说法收敛了一些，而不是推翻它：这 8 个任务里有 6 个，不管哪个臂，基本上*什么都没发生*——A、D、V 的成功率都接近于零（`fecfabca`、`87f4e0b2`、`57fc6bc5`、`e58cc13d`、`0e390551` 全都是 0/5 或更差），说明这个任务/预算组合对 flash 来说本来就太难了，跟塞了什么东西进去没关系，也就没有空间让召回效应显现出来，不管方向是哪边。这六个里有一个（`600f3a31`）显示召回其实是在拖后腿，而且是单调地拖：A 60%（3/5）→ D 20%（1/5）→ V 0%（0/5）——这是第三种真实的模式（召回本身就有害，verdict 评论让它更有害），跟 `6cbf927e`（召回有帮助，verdict 把这个帮助削弱了）和 `daaede29`（召回不管怎样都只多花钱、没好处）都不一样。把全部 8 个任务汇总起来（150 个 flash 会话）：A 6.0%（3/50），D 16.0%（8/50），V 10.0%（5/50）——D 优于 A、V 差于 D 这两个方向在全样本层面都还成立，跟两任务的 pilot 一致，但在每个臂 n=50 的规模下都还没能过显著性检验（Fisher p=0.20 和 0.55）。这两个任务测出来的方向不是巧合,但*幅度*确实不具代表性——汇总出来的效应主要还是由 `6cbf927e` 一个任务撑着的，读者应该更看重那个定性的规律（在任何一个召回有可测效应可以被削弱的任务上，verdict 评论从来没有赢过纯内容），而不是被这一个任务主导的汇总百分比本身。

两次后续 pilot 加上这次 6 任务的泛化检查（一共 282 个会话）总花费：¥4.77（¥16.29 → ¥11.52），让整个探索成本 / 信任 / verdict 调查到目前为止的总花费达到 ¥13.09，一共跑了 525 个真实的多轮 agentic 会话。

**对照了一下实际的生产代码，是个好消息：目前不需要改任何东西。** `src/index.ts` 里的 `renderRecall`（`recallForFirstTurn` 实际调用来构造一个真实会话会看到的内容的那个函数）注入的正好是 `{ nodeId, sourceSessionId, capturedThroughSeq, completedAt, score, actions, summary }`——只有内容，不带任何形式的新鲜度或置信度评论。这正是这几次 pilot 里表现最好的那种形状（D 臂），不是这些 pilot 想指出来要修的疏漏。这个发现是在提前警告一个看起来很自然、但接下来可能会做的改动——把这份笔记别处算出来的 `replayChecklist` verdict，直接塞进同一个 JSON 对象里当成多加的一个字段让模型去读——而不是在说今天已经上线的东西要改。等真的要接这条线的时候，这份笔记给出的证据是：应该用 verdict 去决定 `renderRecall` 要不要返回字符串（比如一个 `dead` 或 `locational` 的 verdict，就像现在 `score` 低于 `minScore` 时那样直接抑制召回），而不是把它当成塞进返回字符串里的又一个字段。

**把真正要接线的工作量摸了一遍——比"在 `index.ts` 里调一下 `replayChecklist`"要大得多：`ContextGraphNode`现在压根没有 `replayChecklist`/探针数据这个字段，而看起来最自然的加入位置其实是错的地方。** `graph.ts` 明确写着自己是纯提取（"Pure extraction and ranking for the cross-session context graph"，不做 I/O），它现有的测试（`graph.spec.ts`）也都是直接同步构造 fixture、调用 `buildContextGraph`/`matchContextGraph`，完全没有进程边界。要真正算出一份 replay checklist，需要两个现在整个事件日志里都不存在的事实：这一轮到底碰了哪些文件路径，以及这一轮结束那一刻的 git `HEAD`。这两个都不能等事后在 `buildContextGraph` 里补——光是 `computeScopeRatio` 本身就是一次 `git diff` 子进程调用，如果每次图重建（这个缓存是每次 `session/event` 就失效重建的）都要对每一个历史节点跑一次，就会把一个现在同步、可 mock、纯函数的东西，变成要在 `execFileSync('git', ...)` 上阻塞、而且是按节点数线性增长的东西。正确的捕获时机应该是*只在真实的轮次完成那一刻捕获一次*——也就是 agent loop 里真正 finalize `turn/end` 事件的地方——而不是事后在 `context-graph` 的提取逻辑里补。这是一次 `packages/core/session` 的事件 schema 改动（session 日志是带 `SESSION_FORMAT_VERSION` 版本号的），不是一个只改 `context-graph` 就能完事的改动，真要动它需要跟 `core/agent-loop` 里管轮次完成的那部分逻辑协调，不是可以只在这一个包里改改就了事的。

"碰过哪些文件路径"这一半，实际情况比一开始想的要好办一些：这套 harness 自己的文件工具用的参数形状很少、很固定、也很明确——这是靠读实际的工具定义确认的，不是靠猜。`packages/fs/tool-fs` 里的 `read`、`edit`、`write` 三个工具都用 `file_path` 这个参数名；`packages/fs/tool-str-replace-editor` 里的 `str_replace_editor` 用的是 `path`。做一个"工具名 → 路径参数名"的 `Record<string, string>` 映射表，应用到 `tool/call` 事件本来就已经原样记下来的 `arguments` 上，是精确且安全的——不需要在一个没审计过的 200 多个包的工具生态里到处猜 JSON 字段名；不在映射表里的工具，就干脆不产出探针，退回到今天这种只按年龄判断新鲜度的行为，而不是猜错。这里巧合地跟我自己的 pilot 脚本用的 `path` 这个惯例撞名了，但那是巧合，不是照搬——生产环境的真实工具大多用 `file_path`，这是 pilot harness 之前从没接触过的，因为它一直驱动的是一套写死的合成工具集。

考虑到这背后牵扯的 schema 改动，这不是能在 loop 里顺手改一改就定下来的事：需要单独立一份有明确范围的提案（大概率是单独一份 agent note），先讲清楚 `core/session` 要加什么事件字段、老日志没有这个字段时怎么兼容/迁移，然后才是这份笔记一直在勾勒的、`context-graph` 读取侧的接线工作。把这些记在这里，是为了让下一次接手能直接从这个约束往下做，而不用重新推导一遍"为什么不能直接改 `graph.ts`"这件事。

## 影响

一个 checkpoint 现在能给出一个具体的、可证伪的可信/不可信理由，而不只是年龄。承重区分和 scope-ratio 守卫都是刻意保守的粗粒度启发式，而非正确性证明：尤其是 `scopeRatio`，只要有无关文件发生改动而未被记录为触及路径，就会把一些其实仍然成立的 checkpoint 降级，这是用召回率换取更低的假 `fresh` 率。Phase 2（沙箱化的 exec probe 重放）和 L2 置信层仍是待办；把这个判定接入 `graph.ts` 的节点投影以及 `index.ts` 里的召回注入路径也是待办——这篇笔记只覆盖 probe/判定这个原语本身及其独立测试层，尚未覆盖它与自动召回的集成。
